This module uses the `sai-corp` tenant and the users Alice and Bob that you created in Module 2. Without them, the exercises in this module fail.

====

SAI Corp's tenant is onboarded, users are federated, and role-based access control is enforced. But SAI Corp's teams still cannot do anything with the platform — they need compute. Specifically, they need virtual machines they can provision on demand without filing a ticket.

In this module, you close that gap. As the Sovereign Cloud Corp platform administrator, you review the storage the platform already provisioned, then create the disk images, instance types, and catalog items that make self-service VM provisioning possible. Then Alice, SAI Corp's tenant administrator, deploys a virtual machine from the catalog. Finally, you verify the boundary between the tenant and the platform: Bob can see the VM in his project, but he cannot publish catalog items or define instance types — the menu stays under platform control.

== Learning objectives

By the end of this module, you'll be able to:

* Identify the storage backend, storage tier, and per-tenant storage classes that the platform provisions
* Create disk images and instance types as platform-level building blocks
* Author and publish a `ComputeInstanceCatalogItem` referencing a VM template
* Deploy a virtual machine from the catalog as a tenant administrator
* Verify that tenant users can consume the catalog but cannot change what the platform offers

== Exercise 1: Review the platform storage configuration

Before any tenant can deploy a virtual machine, the platform needs a storage tier. The VM creation workflow in Red Hat cloud extensions requests a tier *by name* when it provisions a boot disk.

You do not have to build that tier. Red Hat cloud extensions configures its storage when the platform is deployed, and it creates a dedicated Kubernetes storage class for every tenant you onboard — including one for `sai-corp`, created the moment you created the tenant in Module 2. In this exercise you inspect what already exists, so you recognize the pieces when Alice orders a VM against them in Exercise 4.

=== Steps

. List the storage classes in the cluster:
+
[source,role=execute]
----
oc get sc
----
+
.Sample output
----
NAME                                                  PROVISIONER                             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
lvms-vg1 (default)                                    topolvm.io                              Delete          WaitForFirstConsumer   true                   12h
ocs-external-storagecluster-ceph-rbd                  openshift-storage.rbd.csi.ceph.com      Delete          WaitForFirstConsumer   true                   13h
ocs-external-storagecluster-ceph-rbd-immediate        openshift-storage.rbd.csi.ceph.com      Delete          Immediate              true                   13h
ocs-external-storagecluster-ceph-rbd-virtualization   openshift-storage.rbd.csi.ceph.com      Delete          Immediate              true                   12h
ocs-external-storagecluster-cephfs                    openshift-storage.cephfs.csi.ceph.com   Delete          Immediate              true                   13h
openshift-storage.noobaa.io                           openshift-storage.noobaa.io/obc         Delete          Immediate              false                  13h
osac-sai-corp-local                                   topolvm.io                              Delete          WaitForFirstConsumer   false                  16s
osac-shared-local                                     topolvm.io                              Delete          WaitForFirstConsumer   false                  12h
osac-system-local                                     topolvm.io                              Delete          WaitForFirstConsumer   false                  12h
----
+
The classes that matter here are the three with the `osac-` prefix. Red Hat cloud extensions creates one per tenant, named `osac-<tenant>-<tier>`:
+
* `osac-shared-local` and `osac-system-local` were created with the platform, for the built-in `shared` and `system` tenants.
* `osac-sai-corp-local` was created automatically when you created the `sai-corp` tenant in Module 2 — you never asked for it.
+
All three use the `topolvm.io` provisioner, the same LVM storage that backs the cluster default `lvms-vg1`. The `ocs-external-storagecluster-*` classes belong to this cluster's external Ceph storage and are not used by Red Hat cloud extensions.

. As the platform administrator, show the storage backend the platform draws from:
+
[source,role=execute]
----
osac --config $HOME/admin get storagebackend
----
+
.Sample output
----
ID                                    DELETING  NAME
01a1acda-b314-7844-8ff6-e17341110f18  -         local
----
+
A *storage backend* is the physical storage the platform can hand out — here a single LVMS backend named `local`. The UUID in your environment differs.

. Show the storage tiers published on top of that backend:
+
[source,role=execute]
----
osac --config $HOME/admin get storagetier
----
+
.Sample output
----
ID     NAME   DESCRIPTION  PROTOCOL  STATE
local  local  -            BLOCK     ACTIVE
----
+
A *storage tier* is the service-level name a tenant orders against: `local`, block protocol, `ACTIVE`. This is the name Alice passes to `--boot-disk-storage-tier` in Exercise 4, and it is what ties her VM's boot disk to the `osac-sai-corp-local` storage class.
+
[NOTE]
====
`get storagebackend` and `get storagetier` are platform-administrator operations on the internal fulfillment API. They work here because `$HOME/admin` logged in with `--private` in Module 2.
====
+
[HINT]
====
You can see the same information in the Red Hat cloud extensions UI. As a *platform administrator*, navigate to *Infrastructure → Storage Tiers* and confirm that the `local` tier is listed with a green status of `Active`.
====

== Exercise 2: Publish VM building blocks to the catalog

A tenant cannot deploy a virtual machine without three platform-level resources: a *disk image* (the OS source), an *instance type* (CPU and memory sizing), and a *catalog item* (the self-service template that ties them together). In this exercise, you create all three as the platform administrator.

=== Steps

. As the platform administrator, create a Fedora disk image from the public container disk registry:
+
[source,role=execute]
----
osac --config $HOME/admin \
  create diskimage \
  --name fedora \
  --source-ref quay.io/containerdisks/fedora:latest \
  --architecture amd64
----

. Verify the disk image reaches `AVAILABLE` status:
+
[source,role=execute]
----
osac --config $HOME/admin get diskimage
----
+
.Sample output
----
NAME    DELETING  SOURCE_REF                            GUEST_OS_FAMILY  ARCHITECTURE  LIFECYCLE  TENANT
fedora  -         quay.io/containerdisks/fedora:latest  LINUX            AMD64         AVAILABLE  shared
----

. Create an instance type that defines the VM sizing — 1 vCPU and 2 GiB RAM:
+
[source,role=execute]
----
osac --config $HOME/admin \
  create instancetype \
  --name small-1-2 \
  --vcpus 1 \
  --memory-gib 2 \
  --description 'Small - 1 vCPU, 2 GiB RAM'
----

. Verify the instance type is active:
+
[source,role=execute]
----
osac --config $HOME/admin \
  get instancetype
----
+
.Sample output
----
NAME       DELETING  VCPUS  MEMORY  GPUS  GPU NAME  STATE   DESCRIPTION
small-1-2  -         1      2       0     -         ACTIVE  Small - 1 vCPU, 2 GiB RAM
----

. Create the catalog item definition file. The catalog item references the `ocp_virt_vm` template, which tells the platform to provision an OpenShift Virtualization VM. All VM parameters (disk image, instance type, boot disk size, etc.) are passed as CLI flags when creating the compute instance:
+
[source,role=execute]
----
cat > ${HOME}/yaml/standard-linux-vm.yaml <<'EOF'
---
"@type": type.googleapis.com/osac.public.v1.ComputeInstanceCatalogItem
metadata:
  name: standard-linux-vm
title: Standard Linux VM
description: Standard Linux virtual machine for tenant workloads
template:
  id: osac.templates.ocp_virt_vm
published: true
EOF
----

. Apply the catalog item:
+
[source,role=execute]
----
osac --config $HOME/admin \
  create -f ${HOME}/yaml/standard-linux-vm.yaml
----
+
.Sample output
----
Created computeinstancecatalogitem name 'standard-linux-vm' and identifier '01a0cef5-8a40-71e7-ad78-17a9ba6f8d13'.
----

. Verify the catalog item is published:
+
[source,role=execute]
----
osac --config $HOME/admin \
  get computeinstancecatalogitem
----
+
.Sample output
----
TENANT  DELETING  PROJECT  ID                                    NAME               TITLE              PUBLISHED
shared  -         -        01a10b45-4a45-7590-8fec-06578ace00e9  standard-linux-vm  Standard Linux VM  true
----
+
Confirm the catalog item shows *true* in the *published* column.

== Exercise 3: Verify tenant networking

When a tenant is created, Red Hat cloud extensions automatically provisions a default virtual network, subnet, and security group. These resources provide the network foundation for virtual machines. In this exercise, Alice logs in and verifies that the networking resources are ready before deploying a VM.

=== Steps

. As Alice (the tenant administrator), verify the auto-provisioned networking resources are ready:
+
[source,role=execute]
----
osac --config $HOME/alice get virtualnetwork
----
+
.Sample output
----
TENANT    DELETING  PROJECT  ID                                    NAME     IPV4-CIDR      IPV6-CIDR  STATE
sai-corp  -         -        01a13050-6fdd-7ca0-aabb-b9fddb3e961e  default  10.200.0.0/16  -          READY
----
+
[source,role=execute]
----
osac --config $HOME/alice get subnet
----
+
.Sample output
----
TENANT    DELETING  PROJECT  ID                                    NAME          VIRTUAL-NETWORK  IPV4-CIDR      IPV6-CIDR  STATE
sai-corp  -         -        01a13050-e83c-7cdc-87e1-00e7768517e5  default-ipv4  default          10.200.0.0/20  -          READY
----
+
[source,role=execute]
----
osac --config $HOME/alice get securitygroup
----
+
.Sample output
----
TENANT    DELETING  PROJECT  ID                                    NAME     VIRTUAL-NETWORK  INGRESS-RULES  EGRESS-RULES  STATE
sai-corp  -         -        01a13050-e852-7063-930b-92257b008611  default  default          0              1             READY
----
+
All three resources should show `READY` status. The typical default CIDR is `10.200.0.0/16` for the virtual network and `10.200.0.0/20` for the subnet.

. Save the subnet and security group IDs for VM creation:
+
[source,role=execute]
----
SUBNET_ID=$(osac --config $HOME/alice get subnet default-ipv4 -o json | jq -r '.id')
SG_ID=$(osac --config $HOME/alice get securitygroup default -o json | jq -r '.id')

echo "SUBNET_ID=${SUBNET_ID}"
echo "SG_ID=${SG_ID}"
----
+
Both values must be UUIDs. If either shows `null`, the networking resources have not finished provisioning — wait a moment and retry.

== Exercise 4: Deploy a virtual machine

Everything is in place: storage, disk image, instance type, catalog item, and tenant networking. In this exercise, Alice deploys a virtual machine from the catalog and verifies it reaches `RUNNING` state with an IP address on the tenant subnet.

=== Steps

. Retrieve the IDs this exercise uses: the `standard-linux-vm` catalog item, and the tenant's default subnet and security group from Exercise 3:
+
[source,role=execute]
----
CATALOG_ID=$(osac --config $HOME/alice get computeinstancecatalogitem standard-linux-vm -o json | jq -r '.id')
SUBNET_ID=$(osac --config $HOME/alice get subnet default-ipv4 -o json | jq -r '.id')
SG_ID=$(osac --config $HOME/alice get securitygroup default -o json | jq -r '.id')

echo "CATALOG_ID=${CATALOG_ID}"
echo "SUBNET_ID=${SUBNET_ID}"
echo "SG_ID=${SG_ID}"
----

. Create a virtual machine from the catalog. The `--user-data` flag passes cloud-init configuration that sets up a guest login account:
+
[source,role=execute,subs="attributes+"]
----
osac --config $HOME/alice create computeinstance \
  --name portal-vm \
  --catalog-item "${CATALOG_ID}" \
  --instance-type small-1-2 \
  --disk-image fedora \
  --boot-disk-size 10 \
  --boot-disk-storage-tier local \
  --run-strategy Always \
  --network-attachment "subnet=${SUBNET_ID},security-groups=${SG_ID}" \
  --user-data '#cloud-config
user: fedora-admin
password: {osac_user_password}
chpasswd:
  expire: false
ssh_pwauth: true'
----
+
.Sample output
----
Created compute instance '01a0d377-5991-7e0e-8b3a-5135683208ec'.
----

. Watch the DataVolume until it reaches `Succeeded`:
+
[source,role=execute]
----
oc get dv "${DV_NAME}" -n "${VM_NS}" -w
----
+
Press `Ctrl+C` when the status shows `Succeeded`.

. Check the VM status:
+
[source,role=execute]
----
osac --config $HOME/alice \
  get computeinstance
----
+
.Sample output
----
TENANT    NAME       STATE    ADDRESS      ...
sai-corp  portal-vm  RUNNING  10.200.0.x   ...
----
+
Repeat the command until the state shows `RUNNING` and an IP address appears in the tenant subnet range (e.g., `10.200.x.x`).

. Verify the underlying KubeVirt resources on the OpenShift cluster:
+
[source,role=execute]
----
oc get vm,vmi -A --no-headers
----
+
The `VirtualMachine` and `VirtualMachineInstance` objects should show `Running`.

. Access the VM serial console (you may need to press `Enter` to see the login prompt):
+
[source,role=execute]
----
osac --config $HOME/alice \
  console serial computeinstance portal-vm
----
+
Log in with username `fedora-admin` and password `{osac_user_password}`.

. Verify that Fedora has been deployed:
+
[source,role=execute]
----
cat /etc/os-release
----
+
.Sample output
----
NAME="Fedora Linux"
VERSION="45 (Cloud Edition)"
RELEASE_TYPE=stable
ID=fedora
VERSION_ID=45
VERSION_CODENAME=""
PRETTY_NAME="Fedora Linux 45 (Cloud Edition)"
...
----

. Disconnect from the VM by typing `exit` and then press `Ctrl+]` to disconnect from the console.

== Exercise 5: Verify the platform and tenant boundary

Everything you built in Exercise 2 — the disk image, the instance type, the catalog item — you built as the *platform administrator*, on top of the storage the platform provisions. Alice then consumed those building blocks to deploy a VM, as *tenant administrator*. That split is not a convention; the platform enforces it.

In this exercise, Bob demonstrates the boundary from the far side. He is a member of `sai-corp-default-project`, so he can see the workloads in it. What he cannot do is change what the platform offers.

[NOTE]
====
Bob's ProjectMembership gives him authority *inside* his project. The boundary worth testing here is not what a member can do to their own workloads, but the one between the tenant and the platform: a tenant consumes the catalog, it does not get to publish to it.
====

=== Steps

. Remind yourself of Bob's identity — note that `tenant-admin` does not appear in the roles:
+
[source,role=execute]
----
osac --config $HOME/bob whoami
----
+
.Sample output
----
Logged in as: bob
Tenant: sai-corp
Roles: offline_access, uma_authorization, default-roles-my realm
----

. Bob can see the VM in his project:
+
[source,role=execute]
----
osac --config $HOME/bob \
  get computeinstance
----
+
.Sample output
----
TENANT    NAME       STATE    ADDRESS      ...
sai-corp  portal-vm  RUNNING  10.200.0.x   ...
----
+
Bob can see Alice's VM — his project membership covers the workloads in `sai-corp-default-project`.

. Bob cannot administer the tenant. Listing users requires a tenant-admin RoleBinding, which only Alice has:
+
[source,role=execute]
----
osac --config $HOME/bob get users
----
+
.Sample output
----
Error: rpc error: code = PermissionDenied desc = permission denied
----

. Bob cannot publish to the catalog. A tenant consumes catalog items; only the platform administrator creates them:
+
[source,role=execute]
----
cat > ${HOME}/yaml/bob-catalog-item.yaml <<'EOF'
---
"@type": type.googleapis.com/osac.public.v1.ComputeInstanceCatalogItem
metadata:
  name: bob-unauthorized-vm
title: Unauthorized VM
description: A tenant user must not be able to publish this
template:
  id: osac.templates.ocp_virt_vm
published: true
EOF

osac --config $HOME/bob create -f ${HOME}/yaml/bob-catalog-item.yaml
----
+
.Sample output
----
Error: rpc error: code = PermissionDenied desc = permission denied
----

. Bob cannot create platform building blocks either. Instance types define what sizes the whole platform offers:
+
[source,role=execute]
----
osac --config $HOME/bob \
  create instancetype \
  --name bob-huge-vm \
  --vcpus 64 \
  --memory-gib 256
----
+
.Sample output
----
Error: rpc error: code = PermissionDenied desc = permission denied
----
+
This is the separation that makes self-service safe. Tenants deploy as much as their quota allows, but the menu they deploy from stays under platform control — a tenant user cannot invent a 64-vCPU instance type for themselves.

== Module summary

SAI Corp can now provision virtual machines on demand through the Red Hat cloud extensions catalog. The platform administrator defined the building blocks once — images, sizing, and the catalog template, on top of platform-provisioned storage — and tenant administrators can consume them repeatedly without platform engineering involvement.

**Key takeaways for Sovereign Cloud Corp:**

* *Storage tiers bridge Kubernetes and the catalog*: The `local` tier links a Kubernetes storage class to the fulfillment workflow. The platform provisions the tier and a per-tenant `osac-<tenant>-local` storage class for you, and the catalog orders boot disks against the tier by name.
* *Catalog items are self-service templates*: A catalog item references a VM template and makes it available in the service catalog. Tenants specify parameters like disk image, instance type, and networking at ordering time via CLI flags.
* *RBAC extends to workloads*: The same RoleBinding and ProjectMembership model from Module 2 governs compute instances. A project member sees and works with the workloads in their project; tenant-level and platform-level operations stay out of reach.
* *Platform admin vs. tenant admin separation*: Storage, images, instance types, and catalog items are platform-level concerns. VM deployment is a tenant-level action. This separation lets platform teams control what is available while tenants control what is deployed.
