= Module 2: Tenant Onboarding and Identity Management
:source-highlighter: rouge
:toc: macro
:toclevels: 2

toc::[]

Sovereign Cloud Corp has signed a new government agency client: SAI Corp. The agency needs a fully isolated tenant on the platform with federated single sign-on through their corporate identity provider. Their IT administrator, Alice, needs tenant-admin authority to manage projects and team access. Their analyst, Bob, needs read-only access to a specific project.

In this module, you onboard SAI Corp as a tenant using the `osac` CLI, configure SSO federation through a Keycloak realm acting as the corporate identity provider, and prove that role-based access control enforces the right boundaries — a viewer can list resources but cannot modify them.

== Learning objectives

By the end of this module, you'll be able to:

* Create a tenant and verify automatic Keycloak organization and namespace provisioning
* Configure an external identity provider for federated SSO
* Onboard users through SSO and understand JIT user provisioning
* Assign tenant-admin and project viewer roles using RoleBindings and ProjectMemberships
* Verify RBAC enforcement: viewers can read but cannot delete

== Exercise 1: Create a tenant and verify onboarding

When a platform administrator creates a tenant in Red Hat cloud extensions, the platform automatically provisions a Keycloak organization, a dedicated namespace, and a break-glass emergency access account. In this exercise, you create the `sai-corp` tenant and verify that all of these resources were provisioned correctly.

=== Steps

. Set up shell variables for this module and save them in `.bashrc`. These values are used throughout all exercises:
+
[source,role=execute]
----
cat << EOF >>${HOME}/.bashrc
export TENANT=sai-corp
export TENANT_ADMIN=alice
export TENANT_USER=bob
export REALM=osac
EOF

source ${HOME}/.bashrc

mkdir -p ${HOME}/osac-demo
----

. Log in to the *Red Hat cloud extensions* platform *internal* fulfillment API as the *platform administrator*:
+
[source,role=execute,subs=attributes]
----
osac login --insecure \
  --issuer="{osac_keycloak_url}/realms/osac" \
  --flow=password \
  --user={osac_admin_user} \
  --password={osac_admin_password} \
  {osac_fulfillment_internal_api_url}
----

. Switch to the *Red Hat cloud extensions* tab on the right.
. Navigate to *Administration* -> *Tenants*.
. Create a new tenant named `sai-corp`. There are no other parameters except for the name.
+
IMPORTANT: Copy and save the break-glass password now. It is displayed only during tenant creation and cannot be retrieved later.

. The Tenant should show `Synced` within a few seconds of creation.

. Switch to the *Terminal* tab.
. Verify the break-glass user was provisioned:
+
[source,role=execute]
----
osac get tenant sai-corp -o json | jq '.spec.break_glass_credentials_secret'
----
+
.Expected output:
[source,json]
----
{
  "id": "01a0812d-96b2-7d94-a25a-f963c40d5322",
  "name": "break-glass-credentials"
}
----

. Verify that Red Hat cloud extensions automatically created a Keycloak organization for the tenant:
+
[source,role=execute,subs=attributes]
----
KC_TOKEN=$(curl -sk -X POST "{osac_keycloak_url}/realms/master/protocol/openid-connect/token" \
  -d "grant_type=password&client_id=admin-cli&username={osac_keycloak_admin_user}&password={osac_keycloak_admin_password}" \
  | jq -r '.access_token')

curl -sk -H "Authorization: Bearer ${KC_TOKEN}" \
  "{osac_keycloak_url}/admin/realms/${REALM}/organizations?search=sai-corp" \
  | jq '[.[] | {id, name, enabled}]'
----
+
.Sample output
[source,json]
----
[
  {
    "id": "823e4c18-7617-4fd8-906e-108293f3d7a4",
    "name": "sai-corp",
    "enabled": true
  }
]
----
+
You should see the `sai-corp` organization with `enabled: true`.

. Confirm the tenant namespace was created on the cluster:
+
[source,role=execute]
----
oc get ns sai-corp
----
+
The namespace should show `Active` status.

== Exercise 2: Set up a corporate identity provider

SAI Corp employees need to authenticate through their corporate identity provider rather than receiving individual platform passwords.

On this lab environment, Red Hat cloud extensions is already using Keycloak as the platform identity provider (realm `osac`).

In this exercise, you create another Keycloak realm that simulates SAI Corp's corporate IdP, then register it with Red Hat cloud extensions so the platform can federate authentication.

You create two users, *Alice* and *Bob*, in the SAI Corp realm. Alice will later be the tenant administrator, and Bob will be a project viewer. For the purposes of this exercise, both users will have the same password, `{osac_user_password}`.

=== Set up Keycloak

[NOTE]
====
This exercise uses the `curl` command to create Keycloak realms, clients, and users. You could also use the Keycloak admin console, but for the purposes of this exercise the CLI is faster and more repeatable.
====

. Obtain a Keycloak admin token:
+
[source,role=execute,subs=attributes]
----
KC_TOKEN=$(curl -sk -X POST "{osac_keycloak_url}/realms/master/protocol/openid-connect/token" \
  -d "grant_type=password&client_id=admin-cli&username={osac_keycloak_admin_user}&password={osac_keycloak_admin_password}" \
  | jq -r .access_token)

echo
echo "Token obtained: ${KC_TOKEN:0:20}..."
----

. Create the `sai-corp-idp` realm to simulate SAI Corp's corporate identity provider:
+
[source,role=execute,subs=attributes]
----
curl -sk -X POST "{osac_keycloak_url}/admin/realms" \
  -H "Authorization: Bearer ${KC_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "realm": "sai-corp-idp",
    "enabled": true,
    "displayName": "SAI Corp Corporate SSO"
  }' -w "Create realm: HTTP %\{http_code}\n" -o /dev/null
----
+
Expected: `HTTP 201` (created) or `HTTP 409` (already exists).

. Create an OIDC client in the `sai-corp-idp` realm for Red Hat cloud extensions federation:
+
[source,role=execute,subs=attributes]
----
curl -sk -X POST "{osac_keycloak_url}/admin/realms/sai-corp-idp/clients" \
  -H "Authorization: Bearer ${KC_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "clientId": "osac-federation",
    "enabled": true,
    "protocol": "openid-connect",
    "publicClient": false,
    "secret": "osac-demo-secret",
    "redirectUris": ["*"],
    "directAccessGrantsEnabled": true,
    "standardFlowEnabled": true
  }' -w "Create client: HTTP %\{http_code}\n" -o /dev/null
----
+
Expected: `HTTP 201` (created) or `HTTP 409` (already exists).

. Create user `alice` in the Sai corporate IdP realm:
+
[source,role=execute,subs=attributes]
----
curl -sk -X POST "{osac_keycloak_url}/admin/realms/sai-corp-idp/users" \
  -H "Authorization: Bearer ${KC_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "username": "alice",
    "firstName": "Alice",
    "lastName": "Sai",
    "email": "alice@sai-corp.example.com",
    "enabled": true,
    "emailVerified": true,
    "credentials": [{"type": "password", "value": "{osac_user_password}", "temporary": false}]
  }' -w "Create alice: HTTP %\{http_code}\n" -o /dev/null
----

. Create user `bob` in the Sai corporate IdP realm:
+
[source,role=execute,subs=attributes]
----
curl -sk -X POST "{osac_keycloak_url}/admin/realms/sai-corp-idp/users" \
  -H "Authorization: Bearer ${KC_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "username": "bob",
    "firstName": "Bob",
    "lastName": "Sai",
    "email": "bob@sai-corp.example.com",
    "enabled": true,
    "emailVerified": true,
    "credentials": [{"type": "password", "value": "{osac_user_password}", "temporary": false}]
  }' -w "Create bob: HTTP %\{http_code}\n" -o /dev/null
----

. Set the OIDC endpoint variables and save them for later exercises:
+
[source,role=execute,subs=attributes]
----
cat << EOF >>${HOME}/.bashrc
export OIDC_CLIENT_ID='osac-federation'
export OIDC_CLIENT_SECRET='osac-demo-secret'
export OIDC_ISSUER='{osac_keycloak_url}/realms/sai-corp-idp'
export OIDC_TOKEN_URL='{osac_keycloak_url}/realms/sai-corp-idp/protocol/openid-connect/token'
export OIDC_AUTHORIZATION_URL='{osac_keycloak_url}/realms/sai-corp-idp/protocol/openid-connect/auth'
EOF

source ${HOME}/.bashrc

echo "OIDC environment saved to $\{HOME}/.bashrc"
----

=== Register the new Identity Provider with Red Hat cloud extensions

. Switch back to the *Red Hat cloud extensions* tab on the right.
. Log out of the platform if you are logged in as platform admin (`{osac_admin_user}`).
. Now log into the Red Hat cloud extensions platform as the the *SAI Corp break glass user*.
+
Use the *break glass credentials* that you saved when you created the tenant.
+
Your user should be `sai-corp-osac-break-glass`.
+
You will be prompted to change your password.
+
While you can change it to anything you want the rest of the lab will be using `{osac_user_password}` so it is recommended to change it to that value for consistency.

. Once logged in you should already be on the *Identity Providers* page.
. Before you can continue you need to create a `Secret` with the client secret to be used for Keycloak.
+
Switch to the *Terminal* tab and log in as the `sai-corp-osac-break-glass` user:
+
[source,role=execute,subs=attributes]
----
osac login --insecure \
  --issuer="https://keycloak-keycloak.{openshift_cluster_ingress_domain}/realms/osac" \
  --flow=password \
  --user=sai-corp-osac-break-glass \
  --password={osac_user_password} \
  https://{osac_fulfillment_internal_api_url}
----

. The Client secret must be stored in a secret of type `value` in Red Hat cloud extensions.
+
Create a secret named `sai-corp-oidc-secret` in the `sai-corp` tenant namespace with the OIDC client secret:
+
[source,role=execute,subs=attributes]
----
echo -n "${OIDC_CLIENT_SECRET}" | osac \
  create secret --name idp-client-secret \
  --type value --from-file=value=-
----
+
.Expected Output
----
Created secret 'idp-client-secret' (ID: 01a0ce65-e2dc-7860-97e2-c1192478de8d).
----

. Verify the secret was created:
+
[source,role=execute,subs=attributes]
----
osac get secret idp-client-secret -o yaml
----
+
.Sample output
[source,yaml]
----
'@type': type.googleapis.com/osac.public.v1.Secret
data:
  value: b3NhYy1kZW1vLXNlY3JldA==
id: 01a0cdbe-6c22-744a-af92-2e4087ca9be1
metadata:
  creation_timestamp: "2026-09-23T10:10:03.934248Z"
  creator: 01a0cdb2-8a38-768d-a47e-e36be3c1a999
  name: idp-client-secret
  tenant: sai-corp
type: SECRET_TYPE_VALUE
----

. Now switch back to the *Red Hat cloud extensions* tab and create a new identity provider with the following properties:
* *Name*: `sai-corp`
* *Title*: `SAI Corp Corporate SSO`
* *Client ID*: `osac-federation`
* *Client Secret*: Select `idp-client-secret` from the dropdown
* *Issuer*: `{osac_keycloak_url}/realms/sai-corp-idp`
* *Authorization URL*: `{osac_keycloak_url}/realms/sai-corp-idp/protocol/openid-connect/auth`
* *Token URL*: `{osac_keycloak_url}/realms/sai-corp-idp/protocol/openid-connect/token`

. The identity provider should reach `Ready` status within a few seconds. If it does not, check the logs of the `fulfillment` pod in the `osac` namespace for errors.

. Switch to the *Terminal* tab and verify the identity provider reaches `Ready` status:
+
[source,role=execute]
----
osac get identityprovider sai-corp --output yaml | grep -E 'phase:|message:|client_id:'
----
+
.Expected output
----
  client_id: osac-federation
  message: 'Identity provider created successfully with alias: sai-corp-sai-corp'
  phase: IDENTITY_PROVIDER_PHASE_READY
----

== Exercise 3: Onboard tenant users via SSO

With the corporate identity provider configured, SAI Corp employees can now authenticate through federated SSO. In this exercise, Alice and Bob log in for the first time using the device flow. Each login automatically adds them to the SAI Corp Keycloak organization. You also trigger JIT (just-in-time) user provisioning by making an API call after each login.

NOTE: The `osac whoami` command reads the local JWT token only — it does not contact the server. To create an OSAC user record, you must make at least one real API call (such as `osac get projects`) after logging in.

=== Steps

==== Onboard Alice

. Switch to the *Terminal* tab and log out any existing session.
. Log out any existing session:
+
[source,role=execute,subs=attributes]
----
osac logout
----

. Start the device flow login for *Alice*:
+
[source,role=execute,subs=attributes]
----
osac login --insecure --address {osac_fulfillment_internal_api_url} --flow device
----
+
The CLI displays a URL and a one-time code. Complete the login in your browser (not the Showroom interface):
+
.. Copy the URL displayed in the terminal
.. Open a new *incognito/private* browser window
.. Paste the URL and press Enter
.. Enter the code that the `osac login` command printed
.. On the login page, enter `alice`, then click *Sign In*
.. On the next login page, click *SAI Corp Corporate SSO* (the federated identity provider) at the bottom.
.. Enter username `alice` and password `{osac_user_password}`, then click *Sign In*
.. Approve the device authorization if prompted
.. Return to the terminal — you should see `Authentication succeeded`
+
IMPORTANT: Always use a fresh incognito window for each device flow login. A cached browser session may use the wrong identity.

. Back in the terminal, confirm Alice's identity:
+
[source,role=execute]
----
osac whoami
----
+
.Expected output
----
Logged in as: alice
Tenant: sai-corp
Roles: offline_access, uma_authorization, default-roles-my realm
----

. Trigger JIT user provisioning by making an API call:
+
[source,role=execute]
----
osac get projects
----
+
.Expected output
----
TENANT    DELETING  PROJECT  NAME  TITLE  STATE
shared    -         -        -     -      ACTIVE
sai-corp  -         -        -     -      ACTIVE
----
+
This creates Alice's OSAC user record on the server. Without this call, Alice would exist only in Keycloak but not in the Red Hat cloud extensions user directory.

. Check if Alice can list users (this requires tenant-admin authority):
+
[source,role=execute]
----
osac get users
----
+
.Expected output
[source]
----
Error: rpc error: code = PermissionDenied desc = permission denied
----

. Log out Alice:
+
[source,role=execute,subs=attributes]
----
osac logout
----

==== Onboard Bob

. Start the device flow login for Bob:
+
[source,role=execute,subs=attributes]
----
osac login --insecure --address {osac_fulfillment_internal_api_url} --flow device
----
+
Complete the login in a *fresh incognito* window:
+
.. Copy the URL displayed in the terminal
.. Open a new *incognito/private* browser window
.. Paste the URL and press Enter
.. Enter the code that the `osac login` command printed
.. On the login page, enter `bob`, then click *Sign In*
.. On the next login page, click *SAI Corp Corporate SSO* (the federated identity provider) at the bottom.
.. Enter username `bob` and password `{osac_user_password}`, then click *Sign In*
.. Approve the device authorization if prompted
.. Return to the terminal — you should see `Authentication succeeded`
+
IMPORTANT: Always use a fresh incognito window for each device flow login. A cached browser session may use the wrong identity.

. Confirm Bob's identity:
+
[source,role=execute]
----
osac whoami
----
+
.Expected output
----
Logged in as: bob
Tenant: sai-corp
Roles: offline_access, uma_authorization, default-roles-my realm
----

. Trigger JIT provisioning for bob:
+
[source,role=execute]
----
osac get projects
----
+
.Expected output
----
TENANT    DELETING  PROJECT  NAME  TITLE  STATE
shared    -         -        -     -      ACTIVE
sai-corp  -         -        -     -      ACTIVE
----

. Verify both users are now members of the SAI Corp Keycloak organization:
+
[source,role=execute,subs=attributes]
----
KC_TOKEN=$(curl -sk -X POST "{osac_keycloak_url}/realms/master/protocol/openid-connect/token" \
  -d "grant_type=password&client_id=admin-cli&username={osac_keycloak_admin_user}&password={osac_keycloak_admin_password}" \
  | jq -r '.access_token')

ORG_ID=$(curl -sk -H "Authorization: Bearer ${KC_TOKEN}" \
  "{osac_keycloak_url}/admin/realms/osac/organizations?search=sai-corp" \
  | jq -r '.[0].id')

curl -sk -H "Authorization: Bearer ${KC_TOKEN}" \
  "{osac_keycloak_url}/admin/realms/osac/organizations/${ORG_ID}/members" \
  | jq '[.[].username]'
----
+
You should see `alice`, `bob`, and the break-glass account in the list.
+
.Expected output
[source]
----
[
  "alice",
  "bob",
  "sai-corp-osac-break-glass"
]
----

== Exercise 4: Assign roles and manage projects

Alice needs tenant-admin authority to manage SAI Corp's projects and team access. Bob needs viewer access to a specific project. In this exercise, you assign roles using the platform's RoleBinding and ProjectMembership resources, then create a project and grant Bob read-only access.

=== Steps

==== Assign Alice as tenant admin

. Log in as the platform administrator:
+
[source,role="execute",subs="attributes"]
----
osac login --insecure \
  --issuer="{osac_keycloak_url}/realms/osac" \
  --flow=password \
  --user={osac_admin_user} \
  --password={osac_admin_password} \
  {osac_fulfillment_internal_api_url}
----

. List the OSAC users and find Alice's UUID:
+
[source,role="execute"]
----
osac get users
----
+
.Expected output
[source]
----
ID                                    DELETING  NAME                       USERNAME                   EMAIL                            ENABLED  TENANT
01a08652-5c6d-7b47-bf5f-09e9bd83d5e1  -         sai-corp-osac-break-glass  sai-corp-osac-break-glass  break-glass@sai-corp.osac.local  true     sai-corp
01a086a9-f7fe-7079-9a83-028d202cedb2  -         alice                      alice                      -                                true     sai-corp
01a086ab-68a0-7bc3-b9fe-1991cef6ae11  -         bob                        bob                        -                                true     sai-corp

* *Name*: `tenant-admin-binding`
* *Users*: Select `alice`
* *Role*: `Tenant Administrator`

[source,role="execute"]

----

.Expected output

      name: alice

  state: ROLE_BINDING_STATE_READY
----
+
Expected: state `ROLE_BINDING_STATE_READY`, role `tenant-admin`.

==== Verify Alice's tenant-admin access

. Log in as Alice via the device flow to prove the `tenant-admin` role is in her token:
+
[source,role="execute",subs="attributes"]
----
osac logout
osac login --insecure --address {osac_fulfillment_internal_api_url} --flow device
----
+
Complete the login in a *fresh incognito* window. Log in with `alice` / `{osac_user_password}`.

. Confirm Alice now has the `tenant-admin` role:
+
[source,role="execute"]
----
osac whoami
----
+
Expected output includes `tenant-admin` in the Roles list:
+
----
Logged in as: alice
Tenant: sai-corp
Roles: tenant-admin, offline_access, uma_authorization, default-roles-my realm
----

. Verify Alice can now list users (this requires `tenant-admin` authority):
+
[source,role="execute"]
----
osac get users
----
+
You should see both `alice` and `bob` in the user list.

osac create -f ${HOME}/osac-demo/sai-project.yaml
----
+
.Expected output
----
Created project with name 'default' and identifier '01a086c1-51b3-7953-a149-334a7d0acf19'.
----

. List projects to confirm creation:
+
[source,role="execute"]
----
osac get projects
----
+
.Expected output
[source]
----
TENANT    DELETING  PROJECT  NAME     TITLE            STATE
shared    -         -        -        -                ACTIVE
sai-corp  -         -        -        -                ACTIVE
sai-corp  -         -        default  Default Project  ACTIVE
----
+
You should see the `default` project in `ACTIVE` state. You may also see a row with  no name — this is the tenant root project, created automatically with the tenant. This is normal. And the `shared` project is a system project that is always present.

. Save the project ID for later use:
+
[source,role="execute"]
----
export PROJ_ID=$(osac get project default -o json | jq -r .id)

echo "PROJ_ID=${PROJ_ID}"

. Grant Bob `viewer` access to the project using a `ProjectMembership`:
+
[source,role="execute"]
----

  tenant: sai-corp
  project: default

  role: PROJECT_MEMBERSHIP_ROLE_VIEWER
  users:
  - name: bob
EOF

osac create -f ${HOME}/osac-demo/bob-membership.yaml
----
+
.Expected output
----

----

+
[source,role="execute"]
----
osac get projectmemberships
----
+
Expected output:
+
----
TENANT    ...  STATE  PROJECT  USERS     ROLE
sai-corp  ...  READY  default  <bob-id>  VIEWER
----

== Exercise 5: Verify RBAC enforcement

The real proof of multi-tenancy is enforcement. In this exercise, you log in as Bob to confirm that a viewer can list projects but cannot delete them. Then you log back in as Alice to clean up the project and membership, demonstrating that tenant-admin authority is required for destructive operations.

=== Steps

==== Verify Bob's viewer restrictions

. Log in as *Bob* via the device flow:
+
[source,role="execute",subs="attributes"]
----
osac logout
osac login --insecure --address {osac_fulfillment_internal_api_url} --flow device
----
+
Complete the login in a *fresh incognito* window. Click *sai-corp-oidc* and enter `bob` / `{osac_admin_password}`.

. Confirm Bob's identity — note that `tenant-admin` does not appear in the roles:
+
[source,role="execute"]
----
osac whoami
----
+
Expected output:
+
----
Logged in as: bob
Tenant: sai-corp
Roles: offline_access, uma_authorization, ...
----

. Bob can list projects (viewer access):
+
[source,role="execute"]
----
osac get projects
----
+
You should see the `default` project in the list.

. Bob cannot delete the project (RBAC enforcement):
+
[source,role="execute"]
----
source ${HOME}/osac-demo/proj-id.sh
osac delete project ${PROJ_ID}
----
+
Expected output:
+
----
Failed to delete project '<PROJ_ID>': rpc error: code = PermissionDenied desc = permission denied
----
+
This `PermissionDenied` error confirms that RBAC is working: a viewer can read but not modify resources.

== Troubleshooting

=== IdP login shows "Unexpected error when authenticating with identity provider"

**Issue**: Browser login redirects to an error page instead of the corporate IdP login form.
+
**Solution**: This usually indicates an issuer mismatch between the identity provider configuration and the Keycloak broker. Verify the OIDC endpoints match:

[source,role="execute"]
----
osac get identityprovider oidc --output yaml | grep -E 'issuer:|authorizationUrl:|tokenUrl:'

=== Logged in as the wrong user

**Issue**: `osac whoami` shows an unexpected username after device flow login. +
**Solution**: Use a fresh incognito/private browser window for every device flow login. A cached browser session reuses the previous identity. Log out and try again with a clean window.

=== `osac get users` returns PermissionDenied

**Issue**: Running `osac get users` fails with PermissionDenied. +
**Solution**: This command requires `tenant-admin` authority. It is expected to fail for regular users like Bob. Only platform administrators and tenant-admins can list users.

== Module summary

SAI Corp is now onboarded with full identity federation and role-based access control. Their employees authenticate through their corporate identity provider, and the platform enforces the boundaries between administrators and viewers.

**Key takeaways for Sovereign Cloud Corp:**

* Tenant creation is fully automated — the platform handles Keycloak organization, namespace, and emergency access provisioning in a single operation
* Identity federation means corporate users never receive platform passwords; authentication flows through their existing IdP
* RBAC operates at two levels: RoleBindings for tenant-wide authority and ProjectMemberships for project-scoped access
* The break-glass account provides emergency access when the corporate IdP is unavailable — its password must be saved at creation time
