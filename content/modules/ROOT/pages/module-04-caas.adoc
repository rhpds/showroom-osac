= Module 4: Cluster as a Service (CaaS)
:source-highlighter: rouge
:toc: macro
:toclevels: 2

toc::[]

SAI Corp's teams can now provision virtual machines on demand through the VMaaS catalog. But their platform engineers also need full OpenShift clusters — for CI/CD pipelines, containerized workloads, and isolated test environments — provisioned with the same self-service experience.

In this module, you enable Cluster as a Service (CaaS) for the OSAC platform. As the Sovereign Cloud Corp platform administrator, you configure Sushy on the bare-metal fabric host so Ironic can manage libvirt VMs as if they were physical servers, register a `BareMetalHost` that points at that Redfish endpoint, and publish the catalog objects that let tenants order clusters on demand. Then Alice, SAI Corp's tenant administrator, places a cluster order. The platform orchestrates a HyperShift Hosted Control Plane whose worker node boots directly onto the registered bare-metal host — no additional manual steps required.

== Learning objectives

By the end of this module, you'll be able to:

* Set up Sushy on the BMF host so Ironic can manage libvirt VMs through Redfish
* Register a `BareMetalHost` pointing at the Sushy/Redfish endpoint
* Wait for Metal3 to inspect and make the host available
* Publish platform catalog objects: `BareMetalInstanceType`, `DiskImage`, `ClusterVersion`, and `ClusterCatalogItem`
* Order a hosted OpenShift cluster as a tenant using the OSAC CLI

== Exercise 0: Set up the BMF VM to host bare metal servers

[NOTE]
====
Once the steps are solid this will be fully automated and no longer necessary in future environments.
====

The bare-metal fabric host (`10.10.10.2`) runs libvirt and Sushy. Sushy emulates a Redfish BMC for each libvirt VM, so Ironic can power-cycle and provision them as if they were physical servers.

Skip this exercise if the bastion already receives a valid Redfish response:

[source,role=execute]
----
curl -sS -o /dev/null -w 'sushy=%{http_code}\n' http://10.10.10.2:8000/redfish/v1/Systems
----

If `sushy=200`, skip to Exercise 1.

Otherwise, connect to the BMF host:

[source,role=execute]
----
sudo ssh 10.10.10.2
----

Install the required packages. `python3-libvirt` must be installed on the system (not in the venv) so Sushy can import it:

[source,role=execute]
----
dnf install -y qemu-kvm libvirt \
  virt-install python3-pip python3-devel gcc \
  pkgconf-pkg-config python3-libvirt \
  coreos-installer
----

Enable the libvirt sockets:

[source,role=execute]
----
systemctl enable --now virtqemud.socket virtnetworkd.socket virtstoraged.socket
----

Create the Python virtual environment. The `--system-site-packages` flag is required so the venv can import the system `libvirt` module:

[source,role=execute]
----
python3 -m venv --system-site-packages /opt/sushy
source /opt/sushy/bin/activate
pip install -U pip
pip install 'sushy-tools==2.1.0'
----

Verify that libvirt and KVM are accessible:

[source,role=execute]
----
virsh -c qemu:///system list --all
ls /dev/kvm
----

Create the Sushy configuration file:

[source,role=execute]
----
mkdir -p /etc/sushy
cat > /etc/sushy/sushy-emulator.conf <<'EOF'
SUSHY_EMULATOR_LISTEN_IP = u'0.0.0.0'
SUSHY_EMULATOR_LISTEN_PORT = 8000
SUSHY_EMULATOR_LIBVIRT_URI = u'qemu:///system'
EOF
----

Create a minimal smoke-test VM (`node1`). This is only a Redfish sanity check — it is not used as a CaaS worker:

[source,role=execute]
----
virt-install --name node1 --memory 1024 --vcpus 2 \
  --disk size=2 --pxe --network network=default \
  --osinfo detect=on,require=off --noautoconsole

virsh list --all
virsh net-list --all
virsh net-start default 2>/dev/null || true
----

Create the systemd unit for Sushy and start it:

[source,role=execute]
----
cat > /etc/systemd/system/sushy-emulator.service <<'EOF'
[Unit]
Description=Sushy Redfish emulator
After=network.target virtqemud.socket

[Service]
ExecStart=/opt/sushy/bin/sushy-emulator --config /etc/sushy/sushy-emulator.conf
Restart=on-failure

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload && systemctl enable --now sushy-emulator
----

Verify that Sushy is responding and lists the `node1` VM:

[source,role=execute]
----
curl -s http://localhost:8000/redfish/v1/Systems | python3 -m json.tool
----

You should see a system UUID (from `node1`). Log out of the BMF host:
[source,role=execute]
----
exit
----

Test Sushy access from the bastion:
[source,role=execute]
----
curl -sS -o /dev/null -w 'sushy=%{http_code}\n' http://10.10.10.2:8000/redfish/v1/Systems
----

`node1` is only a smoke test (1 GiB / 2 GiB). The actual CaaS worker VM is created in Exercise 3.

== Exercise 1: Set up the lab environment

Before running any CaaS workflow, verify the required tools and extract the cluster pull secret. You will log in as the cloud administrator.

=== Steps

. Verify the required tools are available on the bastion:
+
[source,role=execute]
----
oc whoami
oc get nodes -o wide
which oc osac
----
+
All commands must succeed. If `osac` is missing, refer to the credentials page for installation instructions.

. Generate an SSH key pair if one does not already exist:
+
[source,role=execute]
----
test -f ~/.ssh/id_ed25519.pub || ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub
----

. Extract the cluster pull secret from `openshift-config`:
+
[source,role=execute]
----
oc get secret pull-secret -n openshift-config \
  -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d > "${HOME}/pull-secret-cluster.json"

test -s "${HOME}/pull-secret-cluster.json" && echo "Pull secret OK"
----

. Log in to the OSAC private API as the cloud administrator:
+
[source,role=execute,subs=attributes]
----
osac --config $HOME/admin login --insecure --private \
  --address {osac_fulfillment_internal_api_url} \
  --token-script "oc create token -n osac admin"

osac --config $HOME/admin whoami
----
+
[NOTE]
====
The `--private` flag connects to the internal fulfillment API, which exposes cloud-admin-only resources such as `BareMetalInstanceType` and `ClusterVersion`. The tenant public API does not expose these endpoints.
====

. Confirm the current service state — CaaS and BMaaS should both be enabled:
+
[source,role=execute]
----
helm get values osac -n osac 2>/dev/null | grep -A2 'bmaas:\|caas:\|vmaas:'
----
+
.Sample output
----
bmaas:
  enabled: true
caas:
  enabled: true
vmaas:
  enabled: true
----

== Exercise 2: Configure platform networking

You patch Metal3 to watch BMHs in the `osac` namespace and configure the fulfillment service to use the `noop` DNS driver. The `noop` driver is required in RHDP environments that do not have external Route53 access.

=== Steps

. Patch Metal3 to watch `BareMetalHosts` in all namespaces so it can manage hosts in `osac`:
+
[source,role=execute]
----
oc patch provisioning provisioning-configuration \
  --type merge -p '{"spec":{"watchAllNamespaces": true}}'

oc get provisioning provisioning-configuration \
  -o jsonpath='watchAllNamespaces={.spec.watchAllNamespaces}{"\n"}'
----
+
.Sample output
----
watchAllNamespaces=true
----

. Verify that the OSAC inventory is configured for Metal3 and the `osac` namespace:
+
[source,role=execute]
----
oc get secret osac-inventory-config -n osac \
  -o jsonpath='{.data.inventory\.yaml}' | base64 -d
----
+
Expect `type: metal3` and `namespace: osac`.

. Patch the fulfillment ConfigMap to use the `noop` DNS driver:
+
[source,role=execute,subs=attributes]
----
oc -n osac patch cm cluster-fulfillment-ig --type merge -p '{
  "data": {
    "NETWORK_STEPS_COLLECTION": "ci.steps",
    "DNS_CLASS": "dns.noop.dns",
    "EXTERNAL_ACCESS_BASE_DOMAIN": "hosted.cluster-{guid}.dyn.redhatworkshops.io",
    "HOSTED_CLUSTER_BASE_DOMAIN": "hosted.cluster-{guid}.dyn.redhatworkshops.io",
    "HOSTED_CLUSTER_CONTROLLER_AVAILABILITY_POLICY": "SingleReplica",
    "HOSTED_CLUSTER_INFRASTRUCTURE_AVAILABILITY_POLICY": "SingleReplica"
  }
}'
----

. Verify the patch was applied:
+
[source,role=execute]
----
oc get cm cluster-fulfillment-ig -n osac \
  -o jsonpath='DNS={.data.DNS_CLASS} HOSTED={.data.HOSTED_CLUSTER_BASE_DOMAIN}{"\n"}'
----
+
.Sample output
----
DNS=dns.noop.dns HOSTED=hosted.cluster-9872p.dyn.redhatworkshops.io
----

== Exercise 3: Provision a bare-metal worker host

CaaS needs at least one registered `BareMetalHost` before a tenant can order a cluster. In this RHDP lab a libvirt VM on the BMF host acts as a simulated bare-metal server. Sushy exposes it as a Redfish BMC. Metal3 / Ironic inspects and provisions it exactly as it would a physical host.

=== Steps

. Connect to the BMF host and create the worker VM. The disk must be blank — Ironic writes RHCOS to it during provisioning. Use a fixed MAC address so the BMH record stays consistent across reboots:
+
[source,role=execute]
----
sudo ssh 10.10.10.2
----
+
[source,role=execute]
----
# Create the default storage pool if it does not already exist
mkdir -p /var/lib/libvirt/images

virsh -c qemu:///system pool-define-as default dir \
  --target /var/lib/libvirt/images 2>/dev/null || true

virsh -c qemu:///system pool-start default 2>/dev/null || true

virsh -c qemu:///system pool-autostart default

virt-install --name virtual-bmh-1 \
  --memory 8192 --vcpus 4 \
  --disk size=120,format=qcow2,bus=virtio,pool=default \
  --network network=default,mac=52:54:00:ca:aa:01 \
  --boot loader=/usr/share/edk2/ovmf/OVMF_CODE.fd,loader_ro=yes,loader_type=pflash,nvram_template=/usr/share/edk2/ovmf/OVMF_VARS.fd \
  --os-variant rhel9-unknown \
  --import --noautoconsole
----

. Confirm that Secure Boot is off:
+
[source,role=execute]
----
virsh dumpxml virtual-bmh-1 | grep -E 'loader|nvram|secure'
----
+
You want to see `OVMF_CODE.fd` (not `secboot`) and no `secure='yes'`.

. Capture the VM UUID:
+
[source,role=execute]
----
virsh -c qemu:///system domuuid virtual-bmh-1
----

. Log out of the BMF host:
+
[source,role=execute]
----
exit
----

. On the bastion, create the BMC secret and the `BareMetalHost`:
+
[source,role=execute]
----
export VM_UUID=$(sudo ssh 10.10.10.2 virsh -c qemu:///system domuuid virtual-bmh-1)
echo "VM_UUID=${VM_UUID}"

oc apply -f - <<EOF
---
apiVersion: v1
kind: Secret
metadata:
  name: virtual-bmh-1-bmc-secret
  namespace: osac
type: Opaque
stringData:
  username: admin
  password: password
---
apiVersion: metal3.io/v1alpha1
kind: BareMetalHost
metadata:
  name: virtual-bmh-1
  namespace: osac
spec:
  online: true
  bootMACAddress: 52:54:00:ca:aa:01
  bootMode: UEFI
  automatedCleaningMode: metadata
  rootDeviceHints:
    deviceName: /dev/vda
  bmc:
    address: redfish-virtualmedia+http://10.10.10.2:8000/redfish/v1/Systems/${VM_UUID}
    credentialsName: virtual-bmh-1-bmc-secret
    disableCertificateVerification: true
EOF
----

. Label the `BareMetalHost` so OSAC can claim it:
+
[source,role=execute]
----
oc label bmh virtual-bmh-1 -n osac \
  osac.openshift.io/host-type=default --overwrite
----

. Watch the `BareMetalHost` move through `registering` → `inspecting` → `available`. Inspection takes 5–30 minutes:
+
[source,role=execute]
----
watch -n 15 "oc get bmh virtual-bmh-1 -n osac \
  -o custom-columns=NAME:.metadata.name,STATUS:.status.operationalStatus,STATE:.status.provisioning.state,HOST-TYPE:.metadata.labels.osac\\.openshift\\.io/host-type"
----
+
Press `Ctrl+C` when `STATE=available`. The `BareMetalHost` must reach `available` before you proceed.
+
[WARNING]
====
If the `BareMetalHost` stays `inspecting` with no progress, the IPA discovery agent cannot reach Ironic or pull its container images. The most common cause on this lab is that the BMF host's nftables forward policy blocks traffic between the libvirt NAT bridge (`virbr0`) and the hub network or the internet. Contact your instructor if inspection does not complete within 30 minutes.
====

== Exercise 4: Publish cluster catalog objects

With an `available` `BareMetalHost` in the inventory, you can publish the catalog objects tenants need to order a cluster. This exercise covers four resources: the `BareMetalInstanceType` (compute profile), the `DiskImage` (RHCOS OS source), the `ClusterVersion` (OCP release), and the `ClusterCatalogItem` (self-service template).

=== Steps

. Check whether the catalog objects already exist before creating them:
+
[source,role=execute]
----
osac --config $HOME/admin get baremetalinstancetype
osac --config $HOME/admin get diskimage
osac --config $HOME/admin get clusterversion
osac --config $HOME/admin get clustercatalogitem
----

. Create the `BareMetalInstanceType` that describes the worker VM's hardware profile:
+
[source,role=execute]
----
osac --config $HOME/admin create baremetalinstancetype \
  --name c1-metal-amd64 \
  --description "RHDP libvirt+sushy BMH" \
  --cpu-cores 4 \
  --cpu-architecture x86_64 \
  --cpu-threads-per-core 1 \
  --memory-total-gb 8 \
  --network-port enp1s0:fabric:Ethernet:10Gbps \
  --host-label osac.openshift.io/host-type=default

osac --config $HOME/admin get baremetalinstancetype
----
+
.Sample output
----
NAME            CPU_CORES  CPU_ARCH  MEMORY_GB  STATE
c1-metal-amd64  4          x86_64    8          ACTIVE
----
+
[NOTE]
====
The `--cpu-architecture` value must be the string `x86_64`, not the enum `ARCHITECTURE_AMD64`. The `--host-label` must match the label applied to the BMH in Exercise 3.
====

. Create the RHCOS `DiskImage`:
+
[source,role=execute]
----
osac --config $HOME/admin create diskimage \
  --name rhcos-4-22 \
  --source-type registry \
  --source-ref oci://quay.io/osac-project/rhcos:4.22.0 \
  --architecture amd64

osac --config $HOME/admin get diskimage
----
+
.Sample output
----
NAME         DELETING  SOURCE_TYPE  ARCHITECTURE  LIFECYCLE   TENANT
rhcos-4-22   -         REGISTRY     AMD64         AVAILABLE   shared
----

. Create the `ClusterVersion` that links an OCP release image to the disk image:
+
[source,role=execute]
----
osac --config $HOME/admin create clusterversion \
  --version 4.22.0-rhcos \
  --image quay.io/openshift-release-dev/ocp-release:4.22.0-multi \
  --disk-image rhcos-4-22 \
  --enabled

osac --config $HOME/admin get clusterversion
----
+
.Sample output
----
VERSION         IMAGE
4.22.0-rhcos    quay.io/openshift-release-dev/ocp-release:4.22.0-multi
----

. Create and publish the `ClusterCatalogItem`:
+
[source,role=execute]
----
osac --config $HOME/admin create clustercatalogitem \
  --name hosted-ci-small \
  --title "Hosted CI small" \
  --description "Single-replica hosted OCP cluster on bare-metal worker" \
  --template ocp-ci-small \
  --published

osac --config $HOME/admin get clustercatalogitem
----
+
.Sample output
----
NAME              TITLE              PUBLISHED
hosted-ci-small   Hosted CI small    true
----
+
Confirm the item shows `true` in the `PUBLISHED` column before continuing.

== Exercise 5: Order a hosted cluster as Alice

With the catalog objects published, Alice can now self-service a hosted OpenShift cluster without involving the platform team. Alice authenticates through the SAI Corp identity provider using the device flow.

[NOTE]
====
Alice's credentials live in the `sai-corp-idp` Keycloak realm, which is federated into the `osac` realm via identity brokering. The password direct-grant cannot broker federated credentials, so `--flow=password` fails with `invalid_grant`. Use `--flow=device` instead — it redirects through the IdP chain. The device flow stores a token locally; subsequent `osac` commands use that stored token against the internal API, so the OSAC-4519 HTTP/2 issue on the public Route is not a concern.
====

=== Steps

. Log in to the OSAC API as Alice using the device flow:
+
[source,role=execute,subs=attributes]
----
osac --config $HOME/alice login --insecure \
  --issuer="{osac_keycloak_url}/realms/osac" \
  --flow=device \
  {osac_fulfillment_internal_api_url}
----
+
The CLI prints a URL and a short code. Open the *Red Hat cloud extensions* browser tab, navigate to that URL, enter the code, and log in as `alice` / `{osac_user_password}`.
+
[source,role=execute]
----
osac --config $HOME/alice whoami
----
+
.Sample output
----
Logged in as: alice
Tenant: sai-corp
Role: tenant-admin
----

. Confirm that Alice can see the published catalog item:
+
[source,role=execute]
----
osac --config $HOME/alice get clustercatalogitems --filter 'this.published'
----
+
The `hosted-ci-small` catalog item must appear before proceeding.

. Create a pull secret in Alice's tenant so the cluster can pull images from Red Hat registries:
+
[source,role=execute]
----
osac --config $HOME/alice create secret \
  --name cluster-pull-secret \
  --type=pull-secret \
  --from-file=.dockerconfigjson="${HOME}/pull-secret-cluster.json"
----

. Place the cluster order using the catalog item. Run this command exactly once:
+
[source,role=execute]
----
osac --config $HOME/alice create cluster \
  --name sai-corp-caas-1 \
  --catalog-item hosted-ci-small \
  --version 4.22.0-rhcos \
  --node-set "name=workers,size=1,baremetal-instance-type=c1-metal-amd64" \
  --set node_sets.workers.baremetal_instance_type.shared=true \
  --pull-secret cluster-pull-secret \
  --ssh-public-key-file "${HOME}/.ssh/id_ed25519.pub"

osac --config $HOME/alice get cluster
oc get clusterorder -n osac
----
+
.Sample output
----
NAME              STATE
sai-corp-caas-1   Pending
----
+
[IMPORTANT]
====
Do not run `create cluster` a second time. Do not pass `--catalog-item` and `--template` together — the two flags are mutually exclusive.
====

. Watch the provisioning pipeline. The order progresses through these stages:
+
[source,role=execute]
----
watch -n 10 "oc get clusterorder,bmh,bmi,agent -n osac; oc get nodepool -A"
----
+
[cols="1,3",options="header"]
|===
| Stage | What you see

| 1
| ClusterOrder `Progressing`; HostedCluster and NodePool appear

| 2
| `BaremetalInstance` (BMI) created; BMH `CONSUMER` set

| 3
| Ironic `write_image`; BMH state `provisioning`

| 4
| BMH `provisioned`; BMI `Ready`

| 5
| Worker boots; Agent registers → Bound → Validated → Done

| 6
| NodePool `1/1`; order `Ready`; `osac get cluster` shows `READY`
|===
+
Press `Ctrl+C` when the order shows `Ready`. Full provisioning typically takes 20–40 minutes.

. Verify the cluster is reachable. Find the hosted cluster namespace and extract the admin kubeconfig:
+
[source,role=execute]
----
oc get hostedcluster -A
----
+
.Sample output
----
NAMESPACE               NAME              VERSION   PROGRESS   AVAILABLE
osac-order-<id>         sai-corp-caas-1   4.22.0    Completed  True
----
+
[source,role=execute]
----
ORDER_NS=$(oc get hostedcluster -A \
  -o jsonpath='{range .items[?(@.metadata.name=="sai-corp-caas-1")]}{.metadata.namespace}{end}')

oc get secret -n "${ORDER_NS}" \
  -o jsonpath='{range .items[?(@.metadata.name contains "admin-kubeconfig")]}{.metadata.name}{"\n"}{end}'

oc get secret -n "${ORDER_NS}" \
  -o jsonpath='{.items[?(@.metadata.annotations.osac\.openshift\.io/kubeconfig)].data.kubeconfig}' \
  | base64 -d > /tmp/guest.kubeconfig 2>/dev/null \
|| oc get secret sai-corp-caas-1-admin-kubeconfig -n "${ORDER_NS}" \
  -o jsonpath='{.data.kubeconfig}' | base64 -d > /tmp/guest.kubeconfig

oc --kubeconfig=/tmp/guest.kubeconfig --insecure-skip-tls-verify get nodes -o wide
----
+
.Sample output
----
NAME                   STATUS   ROLES    AGE   VERSION
52-54-00-ca-aa-01      Ready    worker   8m    v1.29.x
----
+
A single worker node at `Ready` confirms the hosted cluster is operational.

== Module summary

SAI Corp can now provision hosted OpenShift clusters through the OSAC self-service catalog. The platform administrator defined the hardware profile, OS image, release version, and catalog template once; Alice ordered a cluster without touching any infrastructure configuration.

**Key takeaways for Sovereign Cloud Corp:**

* *HyperShift separates control plane from workers*: The hosted control plane runs as pods on the hub cluster; the worker node is a bare-metal host (or a libvirt VM behind Sushy in this lab). This architecture dramatically reduces the footprint of multi-cluster environments.
* *Sushy + libvirt replaces physical BMCs in the lab*: Sushy emulates a Redfish BMC for each libvirt VM. Ironic interacts with it exactly as it would a real iDRAC or iLO — power-cycle, boot-order, virtual-media ISO. The CaaS workflow is identical for both virtual and physical hardware.
* *BMaaS and CaaS are independently gated*: The Helm chart controls each service with a feature flag. CaaS can be enabled while BMaaS is off, but the `BareMetalInstanceType` and cluster node provisioning both require BMaaS to be on.
* *Catalog items decouple ordering from implementation*: The tenant specifies a `--catalog-item` name; the platform controls which template, OCP version, and hardware profile backs it. Sovereign Cloud Corp can update hardware or OCP versions without changing what tenants see in the catalog.
* *`--catalog-item` replaces `--template` on cluster create*: The `--template` flag is deprecated. Always use `--catalog-item` for cluster orders; the two flags are mutually exclusive.
