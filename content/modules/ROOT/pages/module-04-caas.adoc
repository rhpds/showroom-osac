====
You *must* complete xref:module-02-tenant-management.adoc[Module 2: Tenant Onboarding and Identity Management] before you start this module.

This module uses the `sai-corp` tenant and the users Alice and Bob that you created in Module 2. Without them, the exercises in this module fail.

If you skipped Module 2, go back and either complete its exercises or click the *Solve* button at the end of that module.
====

SAI Corp's teams can now provision virtual machines on demand through the VMaaS catalog. But their platform engineers also need full OpenShift clusters — for CI/CD pipelines, containerized workloads, and isolated test environments — provisioned with the same self-service experience.

In this module, you enable Cluster as a Service (CaaS) for the OSAC platform. As the Sovereign Cloud Corp platform administrator, you will use a pre-configure Sushy emulator on the bare-metal fabric host so Ironic can manage libvirt VMs as if they were physical servers, register a `BareMetalHost` that points at that Redfish endpoint, and publish the catalog objects that let tenants order clusters on demand. Then Alice, SAI Corp's tenant administrator, places a cluster order. The platform orchestrates a HyperShift Hosted Control Plane whose worker node boots directly onto the registered bare-metal host — no additional manual steps required.

== Learning objectives

By the end of this module, you'll be able to:

* Validate the Sushy setup on the BMF host so Ironic can manage libvirt VMs through Redfish
* Register a `BareMetalHost` pointing at the Sushy/Redfish endpoint
* Wait for Metal3 to inspect and make the host available
* Publish platform catalog objects: `BareMetalInstanceType`, `DiskImage`, `ClusterVersion`, and `ClusterCatalogItem`
* Order a hosted OpenShift cluster as a tenant using the OSAC CLI

== Exercise 1: Set up the lab environment

Before running any CaaS workflow, verify the required tools and extract the cluster pull secret. You will log in as the cloud administrator.

=== Steps

. Verify that the Sushy emulator is responding on the BMF host:
+
[source,role=execute]
----
curl -sS -o /dev/null -w 'sushy=%{http_code}\n' http://10.10.10.2:8000/redfish/v1/Systems
----
+
If `sushy=200`, everything is set up properly. If not, refer to the appendix for setup instructions.

. Generate an SSH key pair if one does not already exist:
+
[source,role=execute]
----
test -f ~/.ssh/id_ed25519.pub || ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub
----

. Extract the cluster pull secret from `openshift-config`:
+
[source,role=execute]
----
oc get secret pull-secret -n openshift-config \
  -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d > "${HOME}/pull-secret-cluster.json"

test -s "${HOME}/pull-secret-cluster.json" && echo "Pull secret OK"
----

. Log in to the OSAC private API as the cloud administrator:
+
[source,role=execute,subs="attributes+"]
----
osac --config $HOME/admin \
  login --insecure --private \
  --issuer="https://keycloak-keycloak.{openshift_cluster_ingress_domain}/realms/osac" \
  --flow=password \
  --user={osac_admin_user} \
  --password={osac_admin_password} \
  {osac_fulfillment_internal_api_url}

osac --config $HOME/admin whoami
----
+
[NOTE]
====
The `--private` flag connects to the internal fulfillment API, which exposes cloud-admin-only resources such as `BareMetalInstanceType` and `ClusterVersion`. The tenant public API does not expose these endpoints.
====

. Confirm the current service state — CaaS and BMaaS should both be enabled:
+
[source,role=execute]
----
helm get values osac -n osac 2>/dev/null | grep -A2 'bmaas:\|caas:\|vmaas:'
----
+
.Sample output
----
bmaas:
  enabled: true
caas:
  enabled: true
vmaas:
  enabled: true
----

== Exercise 3: Provision a bare-metal worker host

CaaS needs at least one registered `BareMetalHost` before a tenant can order a cluster. In this environment a libvirt VM on a separate `BMF` Virtual Machine host acts as a simulated bare-metal server. Sushy exposes it as a Redfish BMC. Metal3 / Ironic inspects and provisions it exactly as it would a physical host.

=== Steps

. Connect to the BMF host:
+
[source,role=execute]
----
sudo ssh 10.10.10.2
----

. Create the worker VM. The disk must be blank — Ironic writes RHCOS to it during provisioning. Use a fixed MAC address so the BMH record stays consistent across reboots:
+
[source,role=execute]
----
virt-install --name virtual-bmh-1 \
  --memory 8192 --vcpus 4 \
  --disk size=120,format=qcow2,bus=virtio,pool=default \
  --network network=default,mac=52:54:00:ca:aa:01 \
  --boot loader=/usr/share/edk2/ovmf/OVMF_CODE.fd,loader_ro=yes,loader_type=pflash,nvram_template=/usr/share/edk2/ovmf/OVMF_VARS.fd \
  --os-variant rhel9-unknown \
  --import --noautoconsole
----
+
.Sample Output
----
Starting install...
Allocating 'virtual-bmh-1.qcow2'
Creating domain...
Domain creation completed.
----

. Confirm that Secure Boot is off:
+
[source,role=execute]
----
virsh dumpxml virtual-bmh-1 | grep -E 'loader|nvram|secure'
----
+
.Sample Output
----
      <feature enabled='no' name='secure-boot'/>
    <loader readonly='yes' type='pflash' format='raw'>/usr/share/edk2/ovmf/OVMF_CODE.fd</loader>
    <nvram template='/usr/share/edk2/ovmf/OVMF_VARS.fd' templateFormat='raw' format='raw'>/var/lib/libvirt/qemu/nvram/virtual-bmh-1_VARS.fd</nvram>
----
+
You want to see `OVMF_CODE.fd` (not `secboot`) and no `secure='yes'`.

. Check that the VM is running:
+
[source,role=execute]
----
virsh -c qemu:///system list --all
----
+
.Sample Output
----
 Id   Name            State
-------------------------------
 1    virtual-bmh-1   running
----

. Get information about the running VM:
+
[source,role=execute]
----
virsh -c qemu:///system dominfo virtual-bmh-1
----
+
.Sample Output
----
Id:             1
Name:           virtual-bmh-1
UUID:           22440142-6208-4b37-92a8-916aa7906012
OS Type:        hvm
State:          running
CPU(s):         4
CPU time:       8.9s
Max memory:     8388608 KiB
Used memory:    8388608 KiB
Persistent:     yes
Autostart:      disable
Autostart Once: disable
Managed save:   no

Security DOI:   0
Security label: system_u:system_r:svirt_t:s0:c104,c402 (enforcing)
----

. And finally validate network and mac address:
+
[source,role=execute]
----
virsh -c qemu:///system domiflist virtual-bmh-1
----
+
.Sample Output
----
 Interface   Type      Source    Model    MAC
-------------------------------------------------------------

----

. Your worker VM is ready to be adopted as a Bare Metal Host.
+
Log out of the BMF host:
+
[source,role=execute]
----
exit
----

. Back on the bastion, save the UUID of the worker VM and create the BMC secret and the `BareMetalHost`. The label `osac.openshift.io/host-type: default` is what makes the host available to OSAC: when a tenant orders a cluster, OSAC claims a free `BareMetalHost` whose `host-type` label matches the host label of the requested `BareMetalInstanceType`, which you create with the same label in Exercise 4:
+
[source,role=execute,subs="attributes+"]
----
export VM_UUID=$(sudo ssh 10.10.10.2 virsh -c qemu:///system domuuid virtual-bmh-1)
echo "VM_UUID=${VM_UUID}"

oc apply -f - <<EOF
---
apiVersion: v1
kind: Secret
metadata:
  name: virtual-bmh-1-bmc-secret
  namespace: osac
type: Opaque
stringData:
  username: admin
  password: {osac_user_password}
---
apiVersion: metal3.io/v1alpha1
kind: BareMetalHost
metadata:
  name: virtual-bmh-1
  namespace: osac
  labels:
    osac.openshift.io/host-type: default
spec:
  online: true
  bootMACAddress: 52:54:00:ca:aa:01
  bootMode: UEFI
  automatedCleaningMode: disabled
  rootDeviceHints:
    deviceName: /dev/vda
  bmc:
    address: redfish-virtualmedia+http://10.10.10.2:8000/redfish/v1/Systems/${VM_UUID}
    credentialsName: virtual-bmh-1-bmc-secret
    disableCertificateVerification: true
EOF
----
+
.Sample Output
----
secret/virtual-bmh-1-bmc-secret created
baremetalhost.metal3.io/virtual-bmh-1 created
----
+
[NOTE]
====
Ironic authenticates to the BMC with the credentials in `virtual-bmh-1-bmc-secret`. On a physical server those would be the iDRAC or iLO login. The Sushy emulator in this lab is not configured with an authentication file, so it accepts any username and password. The Secret is still required, because the `BareMetalHost` must reference one.
====

. Watch the `BareMetalHost` move through `registering` → `inspecting` → `available`. Inspection takes approximately 5 minutes:
+
[source,role=execute]
----
watch -n 15 "oc get bmh virtual-bmh-1 -n osac \
  -o custom-columns=NAME:.metadata.name,STATUS:.status.operationalStatus,STATE:.status.provisioning.state,HOST-TYPE:.metadata.labels.osac\\.openshift\\.io/host-type"
----
+
.Sample Output
----
NAME            STATUS   STATE       HOST-TYPE
virtual-bmh-1   OK       available   <none>
----
+
Press `Ctrl+C` when `STATE=available`. The `BareMetalHost` must reach `available` before you proceed.
+
[NOTE]
====
The `BareMetalHost` uses `automatedCleaningMode: disabled`. Disk cleaning runs the IPA agent again between deployments, and that needs the same Ironic-to-agent path you open in the next step. A failed clean drops the host into `deprovisioning` and deletes the `BareMetalInstance`. A lab worker does not need its disk wiped between orders.
====
+
.If the host stays in `inspecting` for more than 10 minutes (expand)
[%collapsible]
====
If the host stays in `inspecting` for more than 10 minutes, the IPA discovery agent on the worker cannot reach Ironic on the hub or `quay.io`. In the RHDP lab this is already handled on the BMF host. In other environments, on the BMF host:

* allow `virbr0` ⇄ `enp2s0` (hub) and `virbr0` ⇄ `enp1s0` (internet) in `inet filter forward`, and masquerade `192.168.122.0/24` out of both;
* DNAT `10.10.10.100:6180` (the IPA rootfs URL on the provisioning VIP) to the node that actually serves it. That is the node running the `metal3` pod (`oc get pods -n openshift-machine-api -o wide | grep '^metal3-'`), not necessarily the VIP holder;
* if `coreos-installer iso kargs show` on the attached ISO has no `ipa-api-url`, add `ipa-api-url=https://10.10.10.100:6385 ipa-insecure=1` with `coreos-installer iso kargs modify -a` and `virsh reboot virtual-bmh-1`.

If inspection already timed out (`ERROR=inspection error`), do *not* `virsh destroy` the VM. Delete the `BareMetalHost`, then re-apply the Secret *and* the `BareMetalHost` from the previous step. The manifest already includes the label.
====

. Verify the return path from Ironic to the IPA agent. During provisioning, Ironic on the hub polls the IPA agent on the worker at `<guest-ip>:9999`. The worker sits on the libvirt network `192.168.122.0/24` behind the BMF host. The lab provisioning makes this path work and keeps it in place across reboots:
+
* a route to `192.168.122.0/24` via the BMF host (`10.10.10.2`) on every hub node, set by the `osac-guest-route` MachineConfigs;
* on the BMF host, firewall rules that let the hub reach the guests on ports `80`, `443`, and `9999`, plus NAT for the guests' own outbound traffic. The libvirt network runs in `open` forward mode, so libvirt adds no firewall rules of its own.
+
Without this path, the `BareMetalHost` stays in `provisioning` while Ironic logs `ConnectTimeout` to port `9999`, and eventually fails.

. Check that the MachineConfig exists on the hub cluster:
+
[source,role=execute]
----
oc get mc | grep osac-guest-route
----
+
.Sample output
----
99-master-osac-guest-route                                                                    3.4.0             5m
99-worker-osac-guest-route                                                                    3.4.
----

Check the route on the hub:
+
[source,role=execute]
----
for NODE in $(oc get nodes -o name); do
  oc debug ${NODE} -q -- chroot /host ip route get 192.168.122.10 | head -1
done
----
+
.Sample output
----
192.168.122.10 via 10.10.10.2 dev br-ex src 10.10.10.10 uid 0
192.168.122.10 via 10.10.10.2 dev br-ex src 10.10.10.11 uid 0
192.168.122.10 via 10.10.10.2 dev br-ex src 10.10.10.12 uid 0
192.168.122.10 via 10.10.10.2 dev br-ex src 10.10.10.20 uid 0
192.168.122.10 via 10.10.10.2 dev br-ex src 10.10.10.21 uid 0
----
+
Check the firewall rule on the BMF host:
+
[source,role=execute]
----
sudo ssh 10.10.10.2 'nft list chain inet filter forward | grep -q "dport.*9999" && echo BMF OK'
----
+
.Sample output
----
BMF OK
----
+
.If either check fails, apply the path by hand (expand)
[%collapsible]
====
These commands do not survive a reboot of the BMF host or a hub node.

Add the route on every hub node. Ironic runs in the host-network `metal3` pod on a control-plane node, and the hub routers run on the workers:

[source,role=execute]
----
for NODE in $(oc get nodes -o name); do
  oc debug ${NODE} -q -- chroot /host ip route replace 192.168.122.0/24 via 10.10.10.2 dev br-ex
done
----

On the BMF host, allow the hub to reach the guests:

[source,role=execute]
----
sudo ssh 10.10.10.2 bash -s <<'EOF'
sysctl -w net.ipv4.ip_forward=1
nft list chain inet filter forward | grep -q 'dport.*9999' || \
  nft insert rule inet filter forward iifname enp2s0 oifname virbr0 ip daddr 192.168.122.0/24 tcp dport '{ 80, 443, 9999 }' ct state new accept
nft list chain inet filter forward | grep 'dport'
EOF
----
====
+
The IPA agent only listens while the host is being provisioned. In Exercise 5, the host reaching `provisioned` confirms the path works.

== Exercise 4: Publish cluster catalog objects

With an `available` `BareMetalHost` in the inventory, you can publish the catalog objects tenants need to order a cluster. This exercise covers four resources: the `BareMetalInstanceType` (compute profile), the `DiskImage` (RHCOS OS source), the `ClusterVersion` (OCP release), and the `ClusterCatalogItem` (self-service template).

=== Steps

. Create the `BareMetalInstanceType` that describes the worker VM's hardware profile:
+
[source,role=execute]
----
osac --config $HOME/admin \
  create baremetalinstancetype \
  --name c1-metal-amd64 \
  --description "RHDP libvirt+sushy BMH" \
  --cpu-cores 4 \
  --cpu-architecture amd64 \
  --cpu-threads-per-core 1 \
  --memory-total-gb 8 \
  --network-port enp1s0:fabric:Ethernet:10Gbps \
  --host-label osac.openshift.io/host-type=default
----
+
.Sample Output
----
Created bare metal instance type 'c1-metal-amd64'.
----

. Validate that the `BareMetalInstanceType` exists:
+
[source,role=execute]
----
osac --config $HOME/admin get baremetalinstancetype
----
+
.Sample output
----
TENANT  DELETING  NAME            ID              CORES  MEMORY  ACCELERATORS  DESCRIPTION
shared  -         c1-metal-amd64  c1-metal-amd64  4      8 GB    -             RHDP libvirt+sushy BMH
----
+
[NOTE]
====
The `--cpu-architecture` value must be one of `amd64`, `arm64` or `s390x`. The server rejects `x86_64` and the enum form `ARCHITECTURE_AMD64`. The `--host-label` must match the label applied to the BMH in Exercise 3.
====

. Validate that the the RHCOS `DiskImage` exists:
+
[source,role=execute]
----
osac --config $HOME/admin \
  get diskimage
----
+
.Sample output
----
NAME        DELETING  ID                                    SOURCE_REF                               GUEST_OS_FAMILY  ARCHITECTURE  LIFECYCLE  TENANT
rhcos-4-22  -         01a1598a-cab0-7046-b8d5-cc6f9bba7ca6  oci://quay.io/osac-project/rhcos:4.22.0  LINUX            AMD64         AVAILABLE  shared
----
+
[NOTE]
====
Note that the image is available in the *shared* tenant - making it available for every tenant on the platform.

If you wanted your own, private image, you could create a `DiskImage` in your tenant and reference it in your `ClusterCatalogItem`. The image must be available to the tenant that orders the cluster.
====

. Validate which `ClusterVersions` exist that link an OCP release image to the disk image:
+
[source,role=execute]
----
osac --config $HOME/admin \
  get clusterversion
----
+
.Sample output
----
NAME    DELETING  VERSION  STATE   ENABLED  DEFAULT  IMAGE
4-20-0  -         4.20.0   ACTIVE  true     false    quay.io/openshift-release-dev/ocp-release:4.20.0-multi
4-22-0  -         4.22.0   ACTIVE  true     true     quay.io/openshift-release-dev/ocp-release:4.22.0-multi
----

. Create and publish the `ClusterCatalogItem`:
+
[source,role=execute]
----
osac --config $HOME/admin \
  create clustercatalogitem \
  --name hosted-ci-small \
  --title "Hosted CI small" \
  --description "Single-replica hosted OCP cluster on bare-metal worker" \
  --template ocp-ci-small \
  --published
----
+
.Sample output
----
Created cluster catalog item '01a162e2-2eab-759f-9802-be93129fb9e7'.
----

. Validate the created `ClusterCatalogItem`:
+
[source,role=execute]
----
osac --config $HOME/admin \
  get clustercatalogitem
----
+
.Sample output
----
TENANT  DELETING  PROJECT  ID                                    NAME             TITLE            PUBLISHED
shared  -         -        01a162e2-2eab-759f-9802-be93129fb9e7  hosted-ci-small  Hosted CI small  true
----
+
Confirm the item shows `true` in the `PUBLISHED` column before continuing. Also notice that the cluster catalog item was created in the *shared* tenant again - making this configuration available for all tenants on the platform.

== Exercise 5: Order a hosted cluster as a tenant administrator (Alice)

+
[source,role=execute]
----

echo "DOMAIN=${DOMAIN}"
echo "HCP_NS=${HCP_NS}"
----
+
.Sample output

----
+
The order goes through these stages. The steps below tell you what to do at each one:
+
[cols="1,3,3",options="header"]
|===
| Stage | What you see | Your action

| 1
| ClusterOrder `Progressing`; HostedCluster and NodePool appear; API VIP assigned

== Exercise 6: Access the hosted cluster

The hosted cluster is running, but nothing outside the lab can reach it yet. This lab uses `dns.noop`, so OSAC never publishes DNS records for the cluster's API or `*.apps` domain. The API VIP (`10.10.10.240`) and the worker (`192.168.122.0/24`) are on private networks.

In this exercise you publish both through the hub cluster's router. The hub's `*.apps` wildcard already resolves publicly, and HyperShift already publishes the hosted cluster's OAuth server as a hub route, so logging in works once the API and console are reachable. On a production platform with a real DNS driver, OSAC publishes these endpoints itself and this exercise is not needed.

. Check that the hub can reach the worker's ingress router. The lab provisioning adds the route and firewall rules this needs: a route to `192.168.122.0/24` on all hub nodes, and `tcp 443` allowed from the hub to the guests on the BMF host. Any HTTP code other than `000` means the path works:
+
[source,role=execute]
----
ROUTER_NODE=$(oc get pods -n openshift-ingress -o wide --no-headers | awk 'NR==1{print $7}')

oc debug node/${ROUTER_NODE} -q -- nsenter -a -t 1 -- \
  curl -k -s -m 5 -o /dev/null -w '%{http_code}\n' https://${GUEST_IP}/
----
+
.Sample output
----

----
+
`503` is the expected answer: the request reached the hosted cluster's own router, but a bare IP address does not match any route, so the router replies "Application is not available". If you get `000`, the hub-side route or the BMF firewall rule for port `443` is missing.
+
.If the check returns `000`, open the path by hand (expand)
[%collapsible]
====
Two pieces are needed for the hub router to reach the worker's ingress router at `<guest-ip>:443`.

*1. A route from every hub node to the guest network.* The hub's ingress routers run with `hostNetwork: true` on the worker nodes, so they use each node's own routing table. The lab provisioning adds `192.168.122.0/24 via 10.10.10.2 dev br-ex` (`10.10.10.2` is the BMF host) on every node through the `osac-guest-route` MachineConfigs. Check it, and add it by hand if it is missing:

[source,role=execute]
----
oc get mc | grep osac-guest-route

for NODE in $(oc get nodes -o name); do
  oc debug ${NODE} -q -- chroot /host ip route replace 192.168.122.0/24 via 10.10.10.2 dev br-ex
done
----

*2. A firewall rule on the BMF host that lets the traffic through.* Packets from the hub arrive on the BMF host's `enp2s0` (hub network) and leave on `virbr0` (libvirt bridge). The BMF host's forwarding chain `inet filter forward` has policy `drop`, so it needs an accept rule for ports `80` and `443` towards the guests. The libvirt network runs in `open` forward mode, so there is no separate libvirt firewall to open:

[source,role=execute]
----
sudo ssh 10.10.10.2 bash -s <<'EOF'
nft list chain inet filter forward | grep -q 'dport.*443' || \
  nft insert rule inet filter forward iifname enp2s0 oifname virbr0 ip daddr 192.168.122.0/24 tcp dport '{ 80, 443, 9999 }' ct state new accept
nft list chain inet filter forward | grep 'dport'
EOF
----

These manual changes do not survive a reboot. Run the check above again; it now returns `503`.

. Provide a trusted TLS certificate for the console's public hostname. The hosted cluster's own router only has a certificate for `*.apps.<order>.hosted...`, which does not match the new name. The console operator checks its route over TLS and reports `Available=False` until the certificate matches, and the order does not become `Ready` while that is the case.
+
The hub's own ingress certificate is a publicly trusted wildcard for `*.apps.cluster-<guid>...`, which covers the console's new hostname. Reuse it. It is needed in two places:
+
* in the `HostedCluster` namespace on the hub, because HyperShift only accepts a serving certificate secret that exists next to the `HostedCluster`, and
* in the hosted cluster's `openshift-config` namespace, where the console operator reads it. Ordinary secrets can be created there; only the cluster-wide `config.openshift.io` objects are managed from the hub.
+
[source,role=execute]
----
HUB_CERT=$(oc get ingresscontroller default -n openshift-ingress-operator -o jsonpath='{.spec.defaultCertificate.name}')

oc get secret ${HUB_CERT} -n openshift-ingress -o json \
  | jq --arg ns ${HCP_NS} '{apiVersion: "v1", kind: "Secret", type: "kubernetes.io/tls",
         metadata: {name: "console-custom-tls", namespace: $ns},
         data: {"tls.crt": .data["tls.crt"], "tls.key": .data["tls.key"]}}' \
  | oc apply -f -

oc get secret ${HUB_CERT} -n openshift-ingress -o json \
  | jq '{apiVersion: "v1", kind: "Secret", type: "kubernetes.io/tls",
         metadata: {name: "console-custom-tls", namespace: "openshift-config"},
         data: {"tls.crt": .data["tls.crt"], "tls.key": .data["tls.key"]}}' \
  | oc --kubeconfig=/tmp/${ORDER}/kubeconfig --server=https://${VIP}:6443 --insecure-skip-tls-verify apply -f -
----

[NOTE]
====
This copies the hub's wildcard private key into the tenant's cluster. That is acceptable in a disposable lab, but not something to do on a shared platform. There, OSAC's DNS integration would publish the hosted cluster's own `*.apps` domain with its own certificate.

Do not request a separate certificate for the console hostname from the hub's DNS-validating ACME issuer. In this environment the DNS provider can leave the `_acme-challenge` record behind, and while it exists the hostname no longer resolves through the wildcard.
====

. Give the hosted cluster's console the public hostname and the certificate. The hub router passes the request through unchanged, so the hosted cluster's own router must recognize the new name. The `componentRoutes` setting tells the console operator to serve the console under that hostname, with the certificate from `console-custom-tls`, and to register the hostname as an OAuth redirect.
+
In a hosted cluster you cannot edit cluster-wide configuration such as `ingresses.config/cluster` directly. A policy rejects the change and asks you to "modify the resource in the HostedCluster object", because the hosted control plane owns that configuration and copies it from the `HostedCluster` object on the hub. So you set `componentRoutes` in the `HostedCluster` spec:
+
[source,role=execute]
----
oc patch hostedcluster ${ORDER} -n ${HCP_NS} --type merge -p \
  "{\"spec\":{\"configuration\":{\"ingress\":{\"componentRoutes\":[{\"name\":\"console\",\"namespace\":\"openshift-console\",\"hostname\":\"${CONSOLE_HOST}\",\"servingCertKeyPairSecret\":{\"name\":\"console-custom-tls\"}}]}}}}"

watch -n 10 "oc --kubeconfig=/tmp/${ORDER}/kubeconfig --server=https://${VIP}:6443 --insecure-skip-tls-verify get route -n openshift-console; oc --kubeconfig=/tmp/${ORDER}/kubeconfig --server=https://${VIP}:6443 --insecure-skip-tls-verify get co console"
----
+
Press `Ctrl+C` when a `console-custom` route shows the new hostname and the `console` operator is `Available`. This takes 1-3 minutes: the hosted control plane first copies the setting into the hosted cluster, then the console operator updates the route and checks it.

. Give the hosted cluster's OAuth server the same trusted certificate. When you log in, the console sends the browser to the hosted cluster's OAuth server, which HyperShift publishes as a `passthrough` route on the hub (`oauth-<hcp-namespace>.apps...`). By default that server presents a certificate from the hosted cluster's internal CA, so the browser warns and `oc login` refuses it. The hub wildcard certificate also covers the OAuth hostname, so add it as a named serving certificate. HyperShift hands named certificates to both the API server and the OAuth server, and picks the right one by hostname:
+
[source,role=execute]
----
OAUTH_HOST=$(oc get route oauth -n ${HCP_NS}-${ORDER} -o jsonpath='{.spec.host}')
echo "OAUTH_HOST=${OAUTH_HOST}"

oc patch hostedcluster ${ORDER} -n ${HCP_NS} --type merge -p \
  "{\"spec\":{\"configuration\":{\"apiServer\":{\"servingCerts\":{\"namedCertificates\":[{\"names\":[\"${OAUTH_HOST}\"],\"servingCertificate\":{\"name\":\"console-custom-tls\"}}]}}}}}"
----
+
.Sample output
----

hostedcluster.hypershift.openshift.io/order-t4p9r patched
----
+
This rolls out the hosted cluster's API server and OAuth server again. For about two minutes, logins fail with `400` or `500` errors while the OAuth server reconnects. Wait until the OAuth route presents the trusted certificate and the login page answers:
+
[source,role=execute]
----
until curl -sS -o /dev/null https://${OAUTH_HOST}/healthz 2>/dev/null; do sleep 15; done
sleep 90
curl -sS -o /dev/null -w 'oauth=%{http_code}\n' https://${OAUTH_HOST}/healthz
----
+
.Sample output
----
oauth=200
----

== Module summary

SAI Corp can now provision hosted OpenShift clusters through the OSAC self-service catalog. The platform administrator defined the hardware profile, OS image, release version, and catalog template once; Alice ordered a cluster without touching any infrastructure configuration.

**Key takeaways for Sovereign Cloud Corp:**

* *HyperShift separates control plane from workers*: The hosted control plane runs as pods on the hub cluster; the worker node is a bare-metal host (or a libvirt VM behind Sushy in this lab). This architecture dramatically reduces the footprint of multi-cluster environments.
* *Sushy + libvirt replaces physical BMCs in the lab*: Sushy emulates a Redfish BMC for each libvirt VM. Ironic interacts with it exactly as it would a real iDRAC or iLO — power-cycle, boot-order, virtual-media ISO. The CaaS workflow is identical for both virtual and physical hardware.
* *BMaaS and CaaS are independently gated*: The Helm chart controls each service with a feature flag. CaaS can be enabled while BMaaS is off, but the `BareMetalInstanceType` and cluster node provisioning both require BMaaS to be on.
* *Catalog items decouple ordering from implementation*: The tenant specifies a `--catalog-item` name; the platform controls which template, OCP version, and hardware profile backs it. Sovereign Cloud Corp can update hardware or OCP versions without changing what tenants see in the catalog.
* *`--catalog-item` replaces `--template` on cluster create*: The `--template` flag is deprecated. Always use `--catalog-item` for cluster orders; the two flags are mutually exclusive.
