= Module 4: Cluster as a Service (CaaS)
:source-highlighter: rouge
:toc: macro
:toclevels: 2

toc::[]

SAI Corp's teams can now provision virtual machines on demand through the VMaaS catalog. But their platform engineers also need full OpenShift clusters — for CI/CD pipelines, containerized workloads, and isolated test environments — provisioned with the same self-service experience.

In this module, you enable Cluster as a Service (CaaS) for the OSAC platform. As the Sovereign Cloud Corp platform administrator, you will use a pre-configure Sushy emulator on the bare-metal fabric host so Ironic can manage libvirt VMs as if they were physical servers, register a `BareMetalHost` that points at that Redfish endpoint, and publish the catalog objects that let tenants order clusters on demand. Then Alice, SAI Corp's tenant administrator, places a cluster order. The platform orchestrates a HyperShift Hosted Control Plane whose worker node boots directly onto the registered bare-metal host — no additional manual steps required.

== Learning objectives

By the end of this module, you'll be able to:

* Validate the Sushy setup on the BMF host so Ironic can manage libvirt VMs through Redfish
* Register a `BareMetalHost` pointing at the Sushy/Redfish endpoint
* Wait for Metal3 to inspect and make the host available
* Publish platform catalog objects: `BareMetalInstanceType`, `DiskImage`, `ClusterVersion`, and `ClusterCatalogItem`
* Order a hosted OpenShift cluster as a tenant using the OSAC CLI

== Exercise 1: Set up the lab environment

Before running any CaaS workflow, verify the required tools and extract the cluster pull secret. You will log in as the cloud administrator.

=== Steps

. Verify that the Sushy emulator is responding on the BMF host:
+
[source,role=execute]
----
curl -sS -o /dev/null -w 'sushy=%{http_code}\n' http://10.10.10.2:8000/redfish/v1/Systems
----
+
If `sushy=200`, everything is set up properly. If not, refer to the appendix for setup instructions.

. Generate an SSH key pair if one does not already exist:
+
[source,role=execute]
----
test -f ~/.ssh/id_ed25519.pub || ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub
----

. Extract the cluster pull secret from `openshift-config`:
+
[source,role=execute]
----
oc get secret pull-secret -n openshift-config \
  -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d > "${HOME}/pull-secret-cluster.json"

test -s "${HOME}/pull-secret-cluster.json" && echo "Pull secret OK"
----

. Log in to the OSAC private API as the cloud administrator:
+
[source,role=execute,subs=attributes]
----
osac --config $HOME/admin \
  login --insecure --private \
  --issuer="https://keycloak-keycloak.{openshift_cluster_ingress_domain}/realms/osac" \
  --flow=password \
  --user={osac_admin_user} \
  --password={osac_admin_password} \
  {osac_fulfillment_internal_api_url}

osac --config $HOME/admin whoami
----
+
[NOTE]
====
The `--private` flag connects to the internal fulfillment API, which exposes cloud-admin-only resources such as `BareMetalInstanceType` and `ClusterVersion`. The tenant public API does not expose these endpoints.
====

. Confirm the current service state — CaaS and BMaaS should both be enabled:
+
[source,role=execute]
----
helm get values osac -n osac 2>/dev/null | grep -A2 'bmaas:\|caas:\|vmaas:'
----
+
.Sample output
----
bmaas:
  enabled: true
caas:
  enabled: true
vmaas:
  enabled: true
----

== Exercise 2: Configure platform networking

You patch Metal3 to watch BMHs in the `osac` namespace and verify that the fulfillment service uses the `noop` DNS driver. The `noop` driver is required in RHDP environments that do not have external Route53 access.

[source,role=execute]

  -o jsonpath='watchAllNamespaces={.spec.watchAllNamespaces}{"\n"}'

== Exercise 3: Provision a bare-metal worker host

CaaS needs at least one registered `BareMetalHost` before a tenant can order a cluster. In this RHDP lab a libvirt VM on the BMF host acts as a simulated bare-metal server. Sushy exposes it as a Redfish BMC. Metal3 / Ironic inspects and provisions it exactly as it would a physical host.

=== Steps

. Connect to the BMF host and create the worker VM. The disk must be blank — Ironic writes RHCOS to it during provisioning. Use a fixed MAC address so the BMH record stays consistent across reboots:
+
[source,role=execute]
----
sudo ssh 10.10.10.2
----
+
[source,role=execute]
----
# Create the default storage pool if it does not already exist
# [root@bmf ~]# virsh -c qemu:///system pool-list --all
# Name      State    Autostart
#-------------------------------
# default   active   yes

# mkdir -p /var/lib/libvirt/images

# virsh -c qemu:///system pool-define-as default dir \
#  --target /var/lib/libvirt/images 2>/dev/null || true

# virsh -c qemu:///system pool-start default 2>/dev/null || true

# virsh -c qemu:///system pool-autostart default

virt-install --name virtual-bmh-1 \
  --memory 8192 --vcpus 4 \
  --disk size=120,format=qcow2,bus=virtio,pool=default \
  --network network=default,mac=52:54:00:ca:aa:01 \
  --boot loader=/usr/share/edk2/ovmf/OVMF_CODE.fd,loader_ro=yes,loader_type=pflash,nvram_template=/usr/share/edk2/ovmf/OVMF_VARS.fd \
  --os-variant rhel9-unknown \
  --import --noautoconsole
----
+
.Sample Output
----

Creating domain...                                                                                                                      |         00:00:00
Domain creation completed.
----

. Confirm that Secure Boot is off:
+
[source,role=execute]
----

----

.Sample Output

. On the bastion, create the BMC secret and the `BareMetalHost`:

[source,role=execute]

echo "VM_UUID=${VM_UUID}"

oc apply -f - <<EOF
---

----

.Sample Output

. Label the `BareMetalHost` so OSAC can claim it:
+
[source,role=execute]
----

  osac.openshift.io/host-type=default --overwrite
----

. Watch the `BareMetalHost` move through `registering` → `inspecting` → `available`. Inspection takes approximately 5 minutes:
+
[source,role=execute]
----
watch -n 15 "oc get bmh virtual-bmh-1 -n osac \
  -o custom-columns=NAME:.metadata.name,STATUS:.status.operationalStatus,STATE:.status.provisioning.state,HOST-TYPE:.metadata.labels.osac\\.openshift\\.io/host-type"
----
+
Press `Ctrl+C` when `STATE=available`. The `BareMetalHost` must reach `available` before you proceed.
+
[NOTE]
====
The `BareMetalHost` uses `automatedCleaningMode: disabled`. Disk cleaning runs the IPA agent again between deployments, and that needs the same Ironic-to-agent path you open in the next step. A failed clean drops the host into `deprovisioning` and deletes the `BareMetalInstance`. A lab worker does not need its disk wiped between orders.
====
+
[TIP]
====
If the host stays in `inspecting` for more than 10 minutes, the IPA discovery agent on the worker cannot reach Ironic on the hub or `quay.io`. In the RHDP lab this is already handled on the BMF host. In other environments, on the BMF host:

* allow `virbr0` ⇄ `enp2s0` (hub) and `virbr0` ⇄ `enp1s0` (internet) in `inet filter forward`, and masquerade `192.168.122.0/24` out of both;
* DNAT `10.10.10.100:6180` (the IPA rootfs URL on the provisioning VIP) to the node that actually serves it. That is the node running the `metal3` pod (`oc get pods -n openshift-machine-api -o wide | grep '^metal3-'`), not necessarily the VIP holder;
* if `coreos-installer iso kargs show` on the attached ISO has no `ipa-api-url`, add `ipa-api-url=https://10.10.10.100:6385 ipa-insecure=1` with `coreos-installer iso kargs modify -a` and `virsh reboot virtual-bmh-1`.

If inspection already timed out (`ERROR=inspection error`), do *not* `virsh destroy` the VM. Delete the `BareMetalHost`, then re-apply the Secret *and* the `BareMetalHost` from the previous step, and label it again.
====

. Verify the return path from Ironic to the IPA agent. During provisioning, Ironic on the hub polls the IPA agent on the worker at `<guest-ip>:9999`. The worker sits on the libvirt NAT network (`192.168.122.0/24`) behind the BMF host. The lab provisioning makes this path work and keeps it in place across reboots: a route to `192.168.122.0/24` via the BMF host on every control-plane node, and firewall rules on the BMF host that let the hub reach port `9999` and keep libvirt NAT from rewriting the agent's replies. Without it, the `BareMetalHost` stays in `provisioning` while Ironic logs `ConnectTimeout` to port `9999`, and eventually fails.
+
Check the route on the hub:
+
[source,role=execute]
----
oc get nncp osac-bmf-guest-route -o jsonpath='{.status.conditions[?(@.type=="Available")].status}{"\n"}'

for NODE in $(oc get nodes -l node-role.kubernetes.io/master -o name); do
  oc debug ${NODE} -q -- chroot /host ip route get 192.168.122.10 | head -1
done
----
+
.Sample output
----
True
192.168.122.10 via 10.10.10.2 dev br-ex src 10.10.10.10 uid 0
192.168.122.10 via 10.10.10.2 dev br-ex src 10.10.10.11 uid 0
192.168.122.10 via 10.10.10.2 dev br-ex src 10.10.10.12 uid 0
----
+
Check the firewall rules on the BMF host:
+
[source,role=execute]
----
sudo ssh 10.10.10.2 'systemctl is-enabled osac-bmf-nft.timer \
  && nft list chain inet filter forward | grep -q "dport.*9999" \
  && nft list chain ip libvirt_network guest_input | grep -q "dport.*9999" \
  && ! nft list chain ip libvirt_network guest_nat | grep masquerade | grep -vq "ct state new" \
  && echo BMF OK'
----
+
.Sample output
----
enabled
BMF OK
----
+
.If either check fails, apply the path by hand (expand)
[%collapsible]
====
These commands are lost after a reboot of the BMF host or a hub control-plane node. Do *not* run `systemctl reload nftables` on the BMF host afterwards.

Add a route to the guest network on every control-plane node. Ironic runs in the host-network `metal3` pod, which can be rescheduled to any control-plane node:
[source,role=execute]
----
for NODE in $(oc get nodes -l node-role.kubernetes.io/master -o name); do
  oc debug ${NODE} -q -- nsenter -a -t 1 -- sh -c \
    'ip route replace 192.168.122.0/24 via 10.10.10.2 dev br-ex && ip route show 192.168.122.0/24'
done
----
.Sample output
----
192.168.122.0/24 via 10.10.10.2 dev br-ex
192.168.122.0/24 via 10.10.10.2 dev br-ex
192.168.122.0/24 via 10.10.10.2 dev br-ex
----
On the BMF host, allow the traffic through the host firewall and the libvirt firewall, and limit libvirt's NAT to new outbound connections:
[source,role=execute]
----
sudo ssh 10.10.10.2 bash -s <<'EOF'
nft insert rule inet filter forward iifname enp2s0 oifname virbr0 ip daddr 192.168.122.0/24 tcp dport 9999 ct state new accept
nft insert rule inet filter forward iifname enp2s0 oifname virbr0 icmp type echo-request accept
nft insert rule ip libvirt_network guest_input oif virbr0 ip daddr 192.168.122.0/24 tcp dport 9999 accept
nft add rule ip libvirt_network guest_nat meta l4proto '{ tcp, udp }' ip saddr 192.168.122.0/24 ip daddr != 192.168.122.0/24 ct state new masquerade to :1024-65535
nft add rule ip libvirt_network guest_nat ip saddr 192.168.122.0/24 ip daddr != 192.168.122.0/24 ct state new masquerade
sysctl -w net.ipv4.conf.enp2s0.rp_filter=0 net.ipv4.conf.virbr0.rp_filter=0
nft -a list chain ip libvirt_network guest_nat
EOF
----
libvirt's default `guest_nat` chain masquerades guest traffic without checking connection state, which rewrites the agent's replies to Ironic so they arrive from the wrong address. Delete libvirt's original `masquerade` rules, the ones *without* `ct state new`, so only the two rules you just added remain:
[source,role=execute]
----
sudo ssh 10.10.10.2 bash -s <<'EOF'
for H in $(nft -a list chain ip libvirt_network guest_nat \
    | awk '/masquerade/ && !/ct state new/ {print $NF}'); do
  nft delete rule ip libvirt_network guest_nat handle ${H}
done
nft list chain ip libvirt_network guest_nat | grep masquerade
EOF
----
.Sample output
----
		meta l4proto { tcp, udp } ip saddr 192.168.122.0/24 ip daddr != 192.168.122.0/24 ct state new masquerade to :1024-65535
		ip saddr 192.168.122.0/24 ip daddr != 192.168.122.0/24 ct state new masquerade
----
====
+
The IPA agent only listens while the host is being provisioned. In Exercise 5, the host reaching `provisioned` confirms the path works.

== Exercise 4: Publish cluster catalog objects

With an `available` `BareMetalHost` in the inventory, you can publish the catalog objects tenants need to order a cluster. This exercise covers four resources: the `BareMetalInstanceType` (compute profile), the `DiskImage` (RHCOS OS source), the `ClusterVersion` (OCP release), and the `ClusterCatalogItem` (self-service template).

=== Steps

. Create the `BareMetalInstanceType` that describes the worker VM's hardware profile:
+
[source,role=execute]
----
osac --config $HOME/admin create baremetalinstancetype \
  --name c1-metal-amd64 \
  --description "RHDP libvirt+sushy BMH" \
  --cpu-cores 4 \
  --cpu-architecture x86_64 \
  --cpu-threads-per-core 1 \
  --memory-total-gb 8 \
  --network-port enp1s0:fabric:Ethernet:10Gbps \
  --host-label osac.openshift.io/host-type=default

osac --config $HOME/admin get baremetalinstancetype
----
+
.Sample output
----
TENANT  DELETING  NAME            ID              CORES  MEMORY  ACCELERATORS  DESCRIPTION
shared  -         c1-metal-amd64  c1-metal-amd64  4      8 GB    -             RHDP libvirt+sushy BMH
----
+
[NOTE]
====
The `--cpu-architecture` value must be the string `x86_64`, not the enum `ARCHITECTURE_AMD64`. The `--host-label` must match the label applied to the BMH in Exercise 3.
====

. Validate that the the RHCOS `DiskImage` exists:
+
[source,role=execute]
----
osac --config $HOME/admin get diskimage
----
+
.Sample output

== Exercise 5: Order a hosted cluster as Alice

[source,role=execute,subs=attributes]

  --flow=device \
  {osac_fulfillment_internal_api_url}
----
+

The hosted cluster is running, but nothing outside the lab can reach it yet. This lab uses `dns.noop`, so OSAC never publishes DNS records for the cluster's API or `*.apps` domain. The API VIP (`10.10.10.240`) and the worker (`192.168.122.0/24`) are on private networks.

*2. Firewall rules on the BMF host that let the traffic through.* Packets from the hub arrive on the BMF host's `enp2s0` (hub network) and leave on `virbr0` (libvirt bridge). Two separate firewalls sit on that path:

* `inet filter forward` is the BMF host's own forwarding chain, with policy `drop`. It already allows `virbr0` → `enp2s0` (the replies) and `tcp 9999` towards the guests, but not `80` or `443`.
* `ip libvirt_network guest_input` is libvirt's chain for traffic *into* the NAT network. It accepts only replies to connections the guests started, and rejects everything else.

`nft insert` puts each rule at the top of its chain, ahead of the `drop` and `reject`. The `grep` guards make the commands safe to run twice:

[source,role=execute]
----
sudo ssh 10.10.10.2 bash -s <<'EOF'
nft list chain inet filter forward | grep -q 'dport.*443' || \
  nft insert rule inet filter forward iifname enp2s0 oifname virbr0 ip daddr 192.168.122.0/24 tcp dport '{ 80, 443 }' ct state new accept
nft list chain ip libvirt_network guest_input | grep -q 'dport.*443' || \
  nft insert rule ip libvirt_network guest_input oif virbr0 ip daddr 192.168.122.0/24 tcp dport '{ 80, 443 }' accept
nft list chain inet filter forward | grep 'dport.*443'
nft list chain ip libvirt_network guest_input | grep 'dport.*443'
EOF
----

----

These BMF rules live in memory only. The `guest_input` rule disappears when libvirt rebuilds its table, for example after a restart of `virtnetworkd`; re-run this command if that happens. Current lab provisioning adds both pieces permanently.

== Module summary

SAI Corp can now provision hosted OpenShift clusters through the OSAC self-service catalog. The platform administrator defined the hardware profile, OS image, release version, and catalog template once; Alice ordered a cluster without touching any infrastructure configuration.

**Key takeaways for Sovereign Cloud Corp:**

* *HyperShift separates control plane from workers*: The hosted control plane runs as pods on the hub cluster; the worker node is a bare-metal host (or a libvirt VM behind Sushy in this lab). This architecture dramatically reduces the footprint of multi-cluster environments.
* *Sushy + libvirt replaces physical BMCs in the lab*: Sushy emulates a Redfish BMC for each libvirt VM. Ironic interacts with it exactly as it would a real iDRAC or iLO — power-cycle, boot-order, virtual-media ISO. The CaaS workflow is identical for both virtual and physical hardware.
* *BMaaS and CaaS are independently gated*: The Helm chart controls each service with a feature flag. CaaS can be enabled while BMaaS is off, but the `BareMetalInstanceType` and cluster node provisioning both require BMaaS to be on.
* *Catalog items decouple ordering from implementation*: The tenant specifies a `--catalog-item` name; the platform controls which template, OCP version, and hardware profile backs it. Sovereign Cloud Corp can update hardware or OCP versions without changing what tenants see in the catalog.
* *`--catalog-item` replaces `--template` on cluster create*: The `--template` flag is deprecated. Always use `--catalog-item` for cluster orders; the two flags are mutually exclusive.

== Appendix: Set up the BMF VM to host bare metal servers

[NOTE]
====
This has already been set up for you in the RHDP lab. You only need to follow these steps if you are running the lab in a different environment or if the Sushy emulator is not responding on the BMF host.
====

The bare-metal fabric host (`10.10.10.2`) runs libvirt and Sushy. Sushy emulates a Redfish BMC for each libvirt VM, so Ironic can power-cycle and provision them as if they were physical servers.

. Connect to the BMF host:
+
[source,role=execute]
----
sudo ssh 10.10.10.2
----

. Install the required packages. `python3-libvirt` must be installed on the system (not in the venv) so Sushy can import it:
+
[source,role=execute]
----
dnf install -y qemu-kvm libvirt \
  virt-install python3-pip python3-devel gcc \
  pkgconf-pkg-config python3-libvirt \
  coreos-installer
----

. Enable the libvirt sockets:
+
[source,role=execute]
----
systemctl enable --now virtqemud.socket virtnetworkd.socket virtstoraged.socket
----

. Create the Python virtual environment. The `--system-site-packages` flag is required so the venv can import the system `libvirt` module:
+
[source,role=execute]
----
python3 -m venv --system-site-packages /opt/sushy
source /opt/sushy/bin/activate
pip install -U pip
pip install 'sushy-tools==2.1.0'
----

. Verify that libvirt and KVM are accessible:
+
[source,role=execute]
----
virsh -c qemu:///system list --all
ls /dev/kvm
----

. Create the Sushy configuration file:
+
[source,role=execute]
----
mkdir -p /etc/sushy
cat > /etc/sushy/sushy-emulator.conf <<'EOF'
SUSHY_EMULATOR_LISTEN_IP = u'0.0.0.0'
SUSHY_EMULATOR_LISTEN_PORT = 8000
SUSHY_EMULATOR_LIBVIRT_URI = u'qemu:///system'
EOF
----

. List the available libvirt networks:
+
[source,role=execute]
----
virsh list --all
----
+
.Sample Output
----
----

. If the network `default` is not running, start it:
+
[source,role=execute]
----
virsh net-start default
----
+
.Sample Output
----
----

. Create the systemd unit for Sushy and start it:
+
[source,role=execute]
----
cat > /etc/systemd/system/sushy-emulator.service <<'EOF'
[Unit]
Description=Sushy Redfish emulator
After=network.target virtqemud.socket

[Service]
ExecStart=/opt/sushy/bin/sushy-emulator --config /etc/sushy/sushy-emulator.conf
Restart=on-failure

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload && systemctl enable --now sushy-emulator
----

. Create a minimal smoke-test VM (`node1`). This is only a Redfish sanity check — it is not used as a CaaS worker:
+
[source,role=execute]
----
virt-install --name node1 --memory 1024 --vcpus 2 \
  --disk size=2 --pxe --network network=default \

----

[source,role=execute]

curl -s http://localhost:8000/redfish/v1/Systems | python3 -m json.tool

----

+
[source,role=execute]
----
